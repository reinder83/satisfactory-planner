# Frontend and redesign guide

Read `../AGENTS.md` first. This guide applies to files in `public/` and to interface redesigns. The goal is a polished, understandable planner that retains the working app's behavior and the owner's existing progress.

## Design freedom

You may redesign colors, typography, spacing, navigation, cards, tables, dialogs and responsive layouts. The current visual style is not a requirement. Prefer familiar labels and clear hierarchy over exposing solver or implementation terminology. Show useful production numbers with units and retain access to detailed inputs, outputs, machine counts and expansion steps.

## Wording

Factories and production lines (#1046, #1047). Use these words in everything a user reads: labels, headings, eyebrows, buttons, notices, toasts and refusal messages, `aria-label`s, titles, ADA's lines, generated step texts, `README.md` and `docs/`.

- A **factory** is a named site of the user's world, such as "Electronics": what the code calls a factory group (`factoryGroups`, `fg-*` ids). The Factories page lists factories ("FACTORY · 3 LINES" over each name, "Edit factories", "+ Add factory", "+ Add to factory…", "Remove factory"); a factory's flow page is "FACTORY · BUILD ORDER"; Logistics is "BETWEEN FACTORIES", with its "Between factories" panel; error messages say "Unknown factory.", "Invalid link between factories.".
- A **production line** is one recipe row of the plan, with its own tick, note and dialog. Spell it out in headings, buttons and sentences ("Production lines", "Production line ↗", "the production line dialog", "Find a production line", "1 of 31 production lines marked running"); "line" or "lines" in counts and short labels ("Electronics · 3 lines", "FACTORY · 1 LINE"). Never call a single line a "factory".
- Lines in no factory are "Ungrouped". "Factory" for the player's whole base in general prose (ADA's asides, "Your factory notebook", the guided start's "sizes the factory") stays as it is.
- A build-plan step of a line has **"Open factory: <factory> →"**, a link to the flow page of the factory the build plan builds the line with (`homeGroup`), and **"Production line ↗"**, the line's dialog; a line in no factory has only the second. "→" goes to another page, "↗" opens a dialog over this one.
- Code identifiers, saved data, routes, storage and check keys, `data-*` hooks and component names keep their old names (`factoryGroups`, `factoryLocal`, `factoryLink()`, `data-calc-factory`, `calcFactory`, `CalcFactoryDialog.vue`, `GroupFlowPage.vue`, `#factories/<group>/flow`); renaming them would need a migration for no user benefit. Comments may keep saying "factory group" for the code's concept. A user's own rewritten step text (`taskEdits`) is theirs and is never reworded.

The interface is being migrated to Vue 3 (see "Vue migration" below). A framework migration must retain both runtime modes, static hosting, save compatibility and functional coverage; do not introduce one merely to reskin the interface.

## Vue migration

The owner chose Vue on 2026-09-24. It lands in stages, one pull request each, and every stage must leave both editions working and every screen behaving as before:

1. Foundation (done): Vite and Vitest, `ui/Shell.vue` (sidebar, navigation, save status, profile footer, top bar, phase picker) and `ui/AdaPanel.vue`.
2. Saves & profiles, account and sign-in, backup (done: `ui/pages/`; `#resources` draws `CalculatedResourcesPage.vue`).
3. Build plan: checklist, step editing, removed steps, deliveries, notes (done: `ui/pages/CalculatedPlanPage.vue` and its parts in `ui/plan/`).
4. Factories: cards, groups and the group editor, and the dialogs for a calculated factory and a group's build order (done; the build-order dialog has since become the group's flow page, #895: `ui/pages/CalculatedFactoriesPage.vue`, `ui/factories/`, and `ui/detail/` mounted into `#detail` by `ui/detail.ts`). The calculated factories page and dialog came forward from stage 6, because they share the cards, groups and flow diagram.
5. Storage room: floors, bays, layout editing, container dialog, workshop (done: `ui/pages/StoragePage.vue`, `ui/storage/`, `ui/detail/SlotDialog.vue`).
6. Calculated resources (done: `ui/pages/CalculatedResourcesPage.vue`, with the notices from `ui/plan/CalcWarnings.vue`).
7. The wizard, in two pull requests by mode (`vuePage` picks a component by `wizard.mode`):
   1. the node survey (done: `ui/pages/SurveyPage.vue`, `ui/survey/`, and the shared form parts in `ui/form/`);
   2. the five steps ("All settings") and the guided start together, since both show the existing-production rows and end on the same Review (done: `ui/pages/WizardPage.vue` with `ui/wizard/`, `ui/pages/GuidedPage.vue` with `ui/guided/`, and the alternate-recipe dialog `ui/detail/AltRecipeDialog.vue`). Every page is now a component, and `render()` no longer draws HTML pages.
8. Cleanup (done): the shared delegated handlers moved into the components (`ui/actions.ts`), and `html.js` is gone with its last users (the boot error screen in `session.ts`, the timeout advice in `wizardError`).

How the parts meet: session state (`session.ts`) is not reactive. `render()` in `shell.ts` mounts the frame once (`ui/mount.ts`) and calls `invalidate()` from `ui/bridge.ts`, then mounts the route's component from `ui/pages.ts` (for `#wizard`, by the draft's mode) into `<main>` as its own app (`mountPage`, synchronous, only when the page changes). A page already shown updates on the next tick, so a handler that needs the redrawn page (to focus a field in it) awaits `nextTick()`. A component reads session state inside `legacy(() => …)`, which re-runs on `invalidate()`. `<main>` has no children in the frame's template, so the frame never touches what is inside it. The sign-in screen (`ui/SignedOut.vue`, `showSignedOut`) and the boot error replace `#app` wholesale and unmount the frame first. The shared `#detail` dialog is a fourth app when it shows a component: `showDetail` in `ui/detail.ts` mounts a fresh one for every opening (so it starts from saved state) and unmounts it when the dialog closes. Every notes box is `ui/NoteBox.vue` (`ui/detail/DetailNote.vue` in a dialog) and keeps its own text, so a redraw (ticking a box in the dialog, the save indicator) does not drop what is being typed. A component that only makes sense for one profile kind must draw nothing, rather than throw, when the other kind is open: switching profiles replaces the session state first, and anything that redraws before `render()` swaps the page (a save finishing, the save indicator) reaches the old page once more. `calcStage()` returns undefined without a calculated profile for the same reason. A busy state goes in a ref bound in the template, never in `el.disabled` on an element whose `disabled` the template also binds: `save()` redraws through the save indicator before its caller resumes, so a handler that resets `el.disabled` afterwards overwrites what that redraw set. Drag and drop (`@dnd-kit/vue`, the storage room): a drop target keeps its id for the life of its component (key it by that id), and the save for a drop waits until the drag operation is idle, because dnd-kit still holds the dragged node and a placeholder beside its place during the drop animation, and a redraw then breaks Vue's patch and leaves the page half drawn (#292). A drop counts only on the position under the pointer (`ui/storage/drop-point.ts`, #298): the cells use a pointer-only collision detector that ignores a pointer outside the window (dnd-kit's default falls back to whatever the dragged card overlaps), and the page saves a drop only when the release point is inside its target's box as drawn then, because after an auto-scroll dnd-kit can still name a position that scrolled away. While a drag lasts, every frame with a scroll measures the positions again and redoes the check (`followScroll` in the same file, bound to the provider's drag-start, #303): dnd-kit does so only when the pointer moves, so under a still pointer the highlight stayed on a position that had scrolled away. `@dnd-kit/vue` reads every `useDroppable` input through `toValue()`, so pass a function-valued option such as the detector as a getter.

The controls several components share bind their handlers from `ui/actions.ts` themselves: `toggleCheck` on every progress checkbox (`@change`, keyed by `data-check`), `factoryLink()` for a link to a factory's dialog (`v-bind`, which sets `data-calc-factory` and the click), `closeDetail` on the × of every dialog and `newSave` on "Create a save". Notes have no button (#237): `ui/note-draft.ts` saves a notes box through `save()` 800 ms after typing stops and when it loses focus, with a status line under it ("Saving…", "Saved · 12:04", "Not saved — Retry", `aria-live="polite"`). "Saving…" shows only while a write is on its way, and Retry moves focus to the note before its button goes (#283). Its textarea carries the notes key as `data-save-note`. A note write names the saved text it was typed over (`base`), and both editions refuse it with 409 when the note now says something else (`checkBase` in `public/state/mutate.ts`, #1052; a write without `base`, from an older page, keeps the revision rule of #165). The box then shows the other version read-only under it with **Keep mine**, **Keep theirs** and **Keep both** (`data-note-keep`), and saves nothing until one is pressed; so does a saved note that changes underneath a draft any other way (the reply to another write, a refresh). Each box registers with `noteBoxes` in `api.ts`, so `allowSwitch()` sends a note still waiting for its pause before the page goes away and asks only about one that could not be saved, and the close-tab warning does the same. A choice that only an explicit Save stores, the Factories page's "Made on site" picker (#930), registers with `choiceDrafts` in `api.ts` the same way, so it is never dropped without a word nor saved by itself: `allowSwitch()` asks about it too (and on "Leave without saving" puts the saved choice back, since a phase change keeps the page), the close-tab warning counts it, and Done editing or folding its group calls `holdUnsavedChoices()`, which keeps the picker on screen, says why in a live region and focuses its Save, with Discard beside it. Keep those data-* attributes: they carry the saved keys, and `browser-check.ts`, the tests and `allowSwitch()` look for them. Only page-wide listeners remain outside components, in `listeners.ts`: broken item artwork, the hash route, the dialog's backdrop and the close-tab warning. The storage page's fixed checklists are build-plan steps without edit tools (`ui/storage/StorageChecklist.vue`), since step edits apply only to the build plan.

The wizard's screens keep the readers in `wizard/`: their inputs are named as before and are not bound to the draft, so `readWizard`, `readGuidedForm` and `readExtraction` read `#wizard-form` exactly as before, and moving on reads the screen being left. Each screen's form is keyed by its step, so a new screen starts from the draft. Vue writes a bound `:value` back on every redraw of the element, not only when it changes, so an input whose component also redraws for its own state (the supply rows' suggestion list, the storage rates' placeholders and filter) uses `v-value` from `ui/form/value.ts`, which sets the value from the draft only when that changes; otherwise typing that has not been read yet would be put back. Each screen handles its own submit and stops it.

Rules for components (see also "TypeScript" in the root `AGENTS.md`): keep class names and structure identical to the markup they replace, so `style.css` needs no change and the rendered layout can be compared with the previous release element by element; keep every `id`, `data-*` hook and form field name that `browser-check.ts` or the tests use; bind a control's handler in its component (`@click`, `@change`), never as a delegated listener on document; never use `v-html` for user text. Template asset URLs are page-relative (`./favicon.svg`), so `vite.config.ts` turns off Vue's asset URL rewriting, and it keeps template whitespace as written (`whitespace: 'preserve'`): Vue's default removes a line break between two inline elements, which is the gap between buttons in a row. Test components with Vitest in `tests/ui/`, mounted through `render()` as the app mounts them, including a hostile name wherever user text appears. happy-dom ignores `selected` set on an `<option>` before it is inserted, so a select takes its value on the `<select>` (`ui/form/SelectField.vue`), and it counts some valid numbers as step mismatches, so the wizard tests stub `reportValidity`.

Secondary actions that do not need their own button go in a ⋯ menu, `ui/ActionMenu.vue` (#238; the profile cards use it for Duplicate, Share and Remove): its items are `role="menuitem"` buttons with `tabindex="-1"`, a destructive one last as `.btn.danger`. It handles the menu-button keys (Enter/Space/ArrowDown open on the first item, ArrowUp on the last, the arrows, Home and End move, Escape closes back to ⋯, Tab closes), a click outside and one open menu at a time, and choosing an item closes it and focuses ⋯ before the item's handler runs, so a confirmation returns there and a removal passes ⋯ to `refocusAfterRemoval()` as its control. Bind `busy` (and `busyText` such as "Copying…") while an item's work runs, since the item itself is out of sight.

Ask for a confirmation with `confirmAction({ title, body, confirmLabel, danger })` from `ui/confirm.ts` (#241), never the browser's `confirm()`: it opens `<dialog id="confirm">` from `index.html` (`ui/ConfirmDialog.vue`), above `#detail` when that is open, and resolves true only for the confirm button; Cancel, Escape and the backdrop answer false. `danger` makes the button red and starts focus on Cancel; focus goes back to the control that asked. A confirmed removal takes that control away with its row, so the handler records its place first with `refocusAfterRemoval(trigger, { row, control, fallback })` from `ui/refocus.ts` (#286) and calls what it returns after the redraw: focus goes to the same control in the next row, else the previous one, else the list’s "Add…" field or tab, else `<main>`. Use it for any new removal, and for any action without a confirmation whose button goes with its row or makes way for another control (#290): Restore on a removed step or a hidden bay or floor, a container’s ✕, a factory’s ✕ per group, a supply row’s Remove, ADA’s Mute/Unmute and the node survey’s Fill/Reset/Undo. Once no row is left the fallback is what came back or took the button’s place (the restored step’s Remove, the floor tab, Unmute), and `scope` keeps the search inside one bay or one factory card. `allowSwitch()` in `api.ts` returns `true` at once when there is nothing to ask and otherwise that promise, so the Escape and hash-route handlers can decide within their event. Component tests answer it by pressing its real buttons with `answerConfirms()` from `tests/ui/setup.ts`.

A control busy with its save or calculation is never `disabled` (#299): Edge and Chrome move focus to `<body>` the moment a focused control becomes disabled, and it stays there once the control is enabled again. Mark it busy instead with `whileBusy(el, work)` from `app/busy.ts` (or `markBusy`, as the wizard's calculation does), or bind a busy ref as `:aria-disabled="flag || undefined"` and return from the handler while it is set. A busy control is aria-disabled (announced as unavailable; `style.css` draws it like a disabled button), a text field is also read-only, and a click on it does nothing, so a second press, or Enter in a field of its form, sends nothing more. A handler that asks something before it starts checks `isBusy(el)` first, and a select changed by a key while it is busy puts the saved value back. Keep `disabled` for a control that has nothing to do, and mark such a button `.unavailable`: `style.css` draws a bare disabled button like a busy one, with the wait cursor, so without it a Save with nothing left to save looks stuck saving (#939). When the action itself leaves its control disabled (a completed room, the first bay's Move left) send focus on with `refocusAfterRemoval()`: the next room's Complete room, the other arrow. When it takes its control away with the page, see the next paragraph. `tests/ui/busy.test.ts` covers each control, with a stand-in for the browsers' focus move that happy-dom lacks.

When an action opens another page or another profile, its control goes with the page it was on, and focus goes to the new page's heading (#304): the h1 of `ui/PageHeader.vue`, which has `tabindex="-1"` (focusable by script, not by Tab) and shows the usual focus ring after a key press only (`:focus-visible`), else `<main>`. One rule covers every page change: `render()` in `shell.ts` calls `focusOpenedPage()` from `ui/refocus.ts` whenever `mountPage` replaced one page with another, and it moves focus only when focus went with the old page (to `<body>` or a removed element). So Open profile, Duplicate, New profile, the wizard's Create profile and Cancel, All settings / Guided start and a link inside a page need no call of their own, while a sidebar link keeps focus after it is followed, as it always has (the frame stays; the user may want the next link), and the first page drawn after loading takes nothing. Every page change starts at the top, Back and Forward included: `listeners.ts` sets `history.scrollRestoration` to `'manual'` once at start-up (#925), so the browser never puts an old offset back after the page is drawn (Chrome did while focus stayed on a sidebar link); only `focusOpenedPage()` brings something else into view. An action that opens another profile on the page already shown (Round up production, Recalculate with transport fuel, #300) redraws rather than replaces it, so it records `refocusOnOpenedPage(button)` before the work and calls what it returns after the redraw. `tests/ui/page-focus.test.ts` covers each action.

Inside the wizard and the guided start, Continue and Back replace the screen's form (it is keyed by step), so the pressed button goes too: focus goes to the new screen's heading (#608), `ui/form/StepHeading.vue`, an h2 with `tabindex="-1"` and `data-step-heading` whose name starts with a visually hidden "Step 2 of 5: ", so a screen reader says where it is. Both pages watch their step and call `focusNewStep()` from `ui/refocus.ts`, which moves focus only when it was lost (a step tab keeps it) and never on the first screen drawn; it scrolls to the top of the page, or brings the step indicator to the top where that would leave the heading below the window or under the estimate's bar (#449). `tests/ui/step-focus.test.ts` covers it.

A link inside `#detail` that puts another dialog in its place (a factory in a flow, the lane advice) takes its focused link away while the dialog stays open, so `replaceDetail()` in `ui/detail.ts` focuses what `showModal()` focuses on opening (#319): the first control that takes focus, the Running box in the sticky header, else the ×. A replaced dialog starts like a freshly opened one; the dialog's h2 is not made focusable. Closing returns focus to the control that opened the first dialog, however many replaced it: the browser does this for a modal dialog, and `detail.ts` records the opener and puts focus back when it was lost, so it holds in the component tests too (`tests/ui/factories.test.ts`, `tests/ui/wizard.test.ts`). A calculated factory's dialog (`ui/detail/CalcFactoryDialog.vue`) is headed as the row's build-plan step is titled (`buildRowName`), and the step's "Production line ↗" names it the same way (`taskLink`; its `aria-label` is "Production line: Wire for Alpha"): a factory group's own line made on site is "Wire for Alpha" there as on the flow page, so the dialog's name (`aria-labelledby="detail-title"`) tells it from the central "Wire" line (#946).

Every `.notice` names one tone (SP-12, #247): `.warn` when something is wrong or at risk and the user should act (an infeasible draft, a power shortfall, a built line waiting on a supplier), `.info` for guidance, tips and instructions (`.blue` is only the stylesheet's older name for it), and `.error` when something failed, drawn like `#toast.error`. Orange is also the brand accent, so warnings are the only orange notices. `tests/ui/notice-tones.test.ts` checks the templates, and `tests/ui/setup.ts` checks every notice a component test leaves drawn. A failed write still reports through the error toast (`role="status"`); an error notice that appears after an action takes `role="status"` too.

## Functional inventory — retain these flows

- Create a named save; use the five-step settings/preferences/goals/resources/review wizard. Top step tabs are clickable, edits survive navigation, and Review recalculates when needed.
- The guided start: a new save opens on a short illustrated card sequence that writes the same settings object the wizard writes. "All settings" is offered on every guided screen and lands on the advanced step that owns the same question, keeping every answer; "Guided start" returns the same way. A save that already has profiles is asked what changed rather than every question again. Guided questions live in `preferences/guided.ts`; their artwork is either an item icon already bundled in `icons/` or inline SVG, never a new asset.
- Production you already run: from Phase 2 on the guided start asks for it as item + rate, and All settings step 1 carries the same control. Its item search is an in-page listbox, not a native `<datalist>`: that popup is browser chrome, so it cannot be themed or verified, and Chrome suppresses it entirely on an input with `autocomplete="off"`. Keep it keyboard-operable (arrows, Enter, Escape) and keep the half-finished rows in `wizard.supplyRows` — the editing rows are not the same as the rows handed to the planner, and picking a suggestion commits a name before any rate exists to go with it. It writes `settings.existingSupply`, which the planner credits; do not replace it with a checklist matched against the plan's own rows, which is what it deliberately is not. Review and the calculated resources page both report what was credited per phase. On Phase 1 the question is the HUB tutorial instead, which writes the existing `early-base-hub` and `unlock-…` keys through `newProfileState`; a profile created without either is the blank state earlier releases produced.
- Select, rename and remove profiles with confirmation. Switching profiles preserves each one's progress. A profile opens (`loadContext()`, for a new profile and an existing one) on its saved working phase, or on the first earlier phase it plans that still has an open check (`openingPhase` in `app/opening-phase.ts`, #570), a milestone-only phase before a calculated profile's start phase included (#759; its build plan, factories and resources pages say so with `ui/plan/MilestoneOnlyNotice.vue`, which offers "Go to Phase N" for the start phase, saved as the phase track saves it, and, when the profile opened there, also says what `OpenedEarlierNotice.vue` would, in its place, with the button going to the saved phase, #786; the build plan of such a phase has no side column). That phase is only shown, never saved: the saved phase stays the one the user picked, and the phase picker saves and shows a new one as before. While it shows an earlier phase, the build plan says why above the build sequence, with the open steps counted, and offers "Go to Phase N" back to the saved phase (`ui/plan/OpenedEarlierNotice.vue`, #666); ADA's `opened-earlier` remark is flavour only. The active-save header/footer must reflect the selected profile rather than the owner's original settings.
- View chronological guidance for Phases 1–5 and post-game, check tasks, record deliveries, save notes and manage custom tasks.
- Notes (`#notes`, `ui/pages/NotesPage.vue`, #243): the save-wide note (`global`) and one box per phase (`phase-<phase>`), the working phase first and open, the others folded but mounted (so `allowSwitch()` still sees every box), and any earlier phase that holds a note. The build plan links there with "Phase notes →"; Backup no longer has a notes box. Last, on a profile migrated from the original plan, "From the original plan" (`ui/notes/UnplacedRecords.vue`, #499) lists as text each tick, note and group assignment in `handbookOrigin.unmapped` that the migration could not place; it only reads, never deletes, and is absent when there are none.
- Find/filter factories; inspect machine counts, rates, inputs, surplus, expansion and unlock guidance. The factories page (`ui/pages/CalculatedFactoriesPage.vue`) filters by status with a row of chips (`ui/factories/FilterChips.vue`, SP-16, #251): All, Not running, Running, then Local when a plan guide builds rows locally, and Held back, each counting what the search found (`statusFilter` in `app/views/factories.ts`). It is a radio group (arrows, Home and End choose; one Tab stop). The choice is `factoryFilter`, view state never saved; it keeps the old status select's values, and one the page has no chip for shows All. An empty result says why and offers All back. Under the toolbar a jump bar (`ui/factories/JumpBar.vue`, SP-17, #252) has a button per group or shared site the page draws, with its running count over what the search found (not the chosen chip); it scrolls to that section and focuses its heading (`focusSection` in `ui/refocus.ts`; the h2 has `tabindex="-1"`), unfolding it first. Each group and shared site folds with the button before its title (`ui/factories/CollapseToggle.vue`, `aria-expanded`/`aria-controls`); a folded section still counts in the chips, the total and the jump bar. What is folded is remembered per save, profile and section in this browser (`planner-collapsed-sections` in localStorage, `sectionCollapsed` in `app/session.ts`), like "Hide completed", and never saved with the profile: nothing stored, or anything unreadable, means all open.
- View the selected storage contract, labeled container locations, floors and collectables/workshop guidance. Existing storage addresses matter to a physically built game layout. The storage search looks on every floor (#240, `storageMatches` in `app/views/storage.ts`): a results list above the grid (`data-find-slot`) switches to a container's floor and focuses its `data-slot` button, the query stays across floor tabs, and hidden bays and floors are left out, so a result never leads to something the room does not draw. Each floor tab shows its Done containers over its named ones ("Ground floor 41/64", named "Ground floor, 41 of 64 done"), and each bay a `.progress-track` under its title beside its "3/8 containers done" (SP-23, #258): both come from `bayProgress`/`floorProgress` in the same file, so they agree, and leave out reserved positions and hidden bays.- Preserve direct container Done checkboxes and room completion. Both write the same four existing `slot-<address>-<step>` keys; room completion skips unselected/reserved positions. Notes save as you type and leave the dialog open; a blank note removes the note key. Item icons are bundled in `icons/` with source attribution.
- Review resource budgets, feasibility, power headroom, transport allowance and fuel requirements. Resource tables show each ore's bundled icon beside its name.
- Work resource budgets out from node counts: a four-screen survey opened from All settings step 4 (`data-open-extraction`), asking miner mark and clock, then per-purity node counts per ore, then crude oil and nitrogen resource wells, then the total less what is already committed. It writes `settings.limits` and records the survey in `settings.extraction` so it can be reopened; the solver reads only `limits`, exactly as before. The counting screens carry the game's two World Randomization settings — the existing `distribution` and `purity` — and fill the counts from them via `presetCounts`/`presetSurvey`, by shifting nodes up or down the purity scale. `startingSurvey` seeds an unstarted survey from those settings; `matchingPreset` reports which world the counts currently are; `resetExtraction` (`data-node-reset`) empties every count while keeping the miner mark and clock, which are equipment and have no zero; it reads the form first and stashes the survey in `wizard.extractionUndo`, which `undoExtractionReset` (`data-node-undo`, rendered in the reset's place) restores and which a preset fill or `leaveExtraction` clears. It is deliberately not gated on `confirm()`: a browser that has been told to block this page's dialogs answers false without showing one, and the button silently does nothing — prefer an undo to a confirmation anywhere in this app. The component tests in `tests/ui/` press the real buttons; do the same when adding one, because a handler that never fires otherwise passes every test. A test asserts each purity reproduces `resourceDefaults` for that setting to the item and that the node total never changes. `knownWorld(purity,distribution)` decides what can be filled: the default distribution for any known purity, and Random for the uniform purities only. Random is a shuffle — it moves which resource sits where, and their purities with it, but not how many nodes each resource has — so under a uniform purity the totals are exactly the default map's, and under a split-keeping purity the totals are right while the split is not. Resource wells are the exception: a well is randomized whole and the map's wells hold different numbers of satellites, so `presetSurvey(purity,base,distribution)` fills nitrogen only on the default distribution and `matchingPreset` identifies a world by its ordinary nodes alone. Do not fill counts for the resource-rich distributions or a random purity: those are seed-dependent and no authoritative table exists. `richShape` says which way each rich distribution pushes the map, in words and deliberately without numbers, because direction is the only thing independent counts agree on; a test asserts it stays number-free. The yield table lives in `preferences/extraction.ts` and is pinned by a test that rebuilds the shipped `DEFAULT_LIMITS` and `PURE_LIMITS` from the known node counts — do not change a rate there without that test agreeing.
- Edit the build plan per profile: reorder steps, rewrite titles/details, link steps to factories, remove and restore steps. Removed and renamed steps keep their checklist keys and completion.
- Rank the alternate recipes a calculated profile does not allow yet by what each would change in the phase's plan (hard-drive payoff, `ui/plan/PayoffPanel.vue` with `app/payoff.ts`, #204). It runs only on request, is stored with the profile rather than in its progress, and changes nothing about the plan: allowing an alternate still means a new calculated profile.

## Implementation constraints

An update must never break existing progress. A redesign that changes saved structures or task identifiers must implement and test the migration requirements in `../AGENTS.md` before release. Keeping old records in storage is insufficient if users can no longer see or use them. Preserve access to original plans and completion history, including where new steps cannot be mapped automatically.

The UI (`app.ts` and the modules in `app/`) uses hash routes (`#plan`, `#factories`, `#logistics`, `#storage`, `#resources`, `#notes`, `#backup`, `#profiles`, `#wizard`, `#account`) and component event handlers. Preserve working deep links. A group's flow page carries the phase it shows, `#factories/<group>/flow?phase=3` (#926; `flowRoute` in `app/session.ts`, which "Build order →" uses), so a new tab, a bookmark or a reload shows that phase's build order: a route followed or opened shows the phase it names (`showRoutePhase`) the way a profile shows the phase it opens on, never saved, from the first phase up to the saved working phase, and any other phase, or none (an address from before #926), leaves the phase shown as it was; `render()` in `shell.ts` then keeps the address naming the phase shown (`replaceShownRoute` in `api.ts`, a `replaceState` that also records the address as the page on screen, which keeping unsaved notes returns to, #968), so after the phase picker or "Go to Phase N" a reload stays there. Before a profile is loaded `flowRoute` names no phase. A Back, Forward, link or typed address that the user cancels in "Leave without saving?" never rewrites the history (#980): `acceptRoute()` in `api.ts` steps back to the page on screen with `history.go()`, by the places of the two entries (`app/history-place.ts`: the Navigation API's entry index where the browser has it, else a place the app writes into each entry's `history.state` as it shows it, which a reload keeps; an entry without one is a new address, the one after the page on screen), and passes over the hashchange of that step (no redraw, no scroll to the top, no focus moved). So the entry the user tried to reach stays where it was, a cancelled link or typed address becoming the entry Forward reaches, and "Leave without saving" steps to it again. Only a history of one entry, with nowhere to step to, has its address put back in place. Keep `history.state` an object when adding to it: the place is one key in it. "← Factories" stays `#factories`, which shows that phase too. Keep `data-*` action hooks and form field names compatible or update all handlers and tests together. Checklist IDs and saved data keys are not visual implementation details: keep them stable.

Use the shared request path and browser API adapter. Do not bypass them with localStorage, cookies, new server calls or hardcoded profile state. Keep calculation in the browser worker for the public version, and preserve transactional saves and explicit profile scope across tabs.

The public deployment is under `/satisfactory-planner/`, while Docker serves `/`. Use URLs that work in both environments. Update the build allowlist for new fonts, icons, scripts or images; never fix only `dist/`. Avoid external CDNs and trackers for ordinary presentation assets. Keep third-party licenses and asset attribution.

User-provided names, notes, tasks and imported values are untrusted text. Continue escaping them before HTML rendering. Build markup as Vue templates, which escape interpolated text: never `v-html` for user text (it is kept for fixed markup such as the guided start's SVG glyphs), and never concatenate HTML strings. The only markup left outside components is fixed (the boot error screen, the calculation-timeout advice); a message shown in it goes in as text or through `esc()`. The component tests in `tests/ui/` render every page, edit mode and dialog with a hostile name and check that no `<x-evil>` element appears; add new screens there. Use safe URL handling for imported links. Preserve keyboard operation, visible focus, labels, semantic buttons, dialog dismissal/focus handling and readable contrast. Tooltips must work without a mouse and must not be obscured by duplicate native `title` tooltips. Do not use `alt` as a tooltip substitute; meaningful image alt text still belongs on images.

Show MW below 1,000 MW and GW where appropriate above that. For machine instructions distinguish total machines, full-speed machines and any adjustable machine, with output rate alongside clock percentage. Honor calculated whole-machine/surplus settings instead of changing the math for visual neatness.
