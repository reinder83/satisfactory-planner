# Frontend and redesign guide

Read `../AGENTS.md` first. This guide applies to files in `public/` and to interface redesigns. The goal is a polished, understandable planner that retains the working app's behavior and the owner's existing progress.

## Design freedom

You may redesign colors, typography, spacing, navigation, cards, tables, dialogs and responsive layouts. The current visual style is not a requirement. Prefer familiar labels and clear hierarchy over exposing solver or implementation terminology. Show useful production numbers with units and retain access to detailed inputs, outputs, machine counts and expansion steps.

The interface is being migrated to Vue 3 (see "Vue migration" below). A framework migration must retain both runtime modes, static hosting, save compatibility and functional coverage; do not introduce one merely to reskin the interface.

## Vue migration

The owner chose Vue on 2026-09-24. It lands in stages, one pull request each, and every stage must leave both editions working and every screen behaving as before:

1. Foundation (done): Vite and Vitest, `ui/Shell.vue` (sidebar, navigation, save status, profile footer, top bar, phase picker) and `ui/AdaPanel.vue`.
2. Saves & profiles, account and sign-in, backup, handbook resources (done: `ui/pages/`).
3. Build plan: checklist, step editing, removed steps, deliveries, notes (both profile kinds) (done: `ui/pages/PlanPage.vue`, `ui/pages/CalculatedPlanPage.vue` and their parts in `ui/plan/`).
4. Factories: cards, groups and the group editor, and one dialog component for the factory, flow, oil campus and group chain views.
5. Storage room: floors, bays, layout editing, container dialog, workshop.
6. Calculated factories and resources, and the calculated factory dialog.
7. The wizard: five steps, guided start, node survey, supply search, recipe picker.
8. Cleanup: remove the legacy page rendering, `html.js` and the leftover delegated handlers, and the rebuild workarounds in `render()`.

How the two layers meet until then: session state (`session.js`) is not reactive. `render()` in `shell.js` mounts the frame once (`ui/mount.js`) and calls `invalidate()` from `ui/bridge.js`. If `ui/pages.js` has a component for the route, `render()` mounts it into `<main>` as its own app (`mountPage`, synchronous, only when the page changes); otherwise it unmounts that app and fills `<main>` synchronously with the legacy page, because some handlers read the page right after calling it. A component reads session state inside `legacy(() => …)`, which re-runs on `invalidate()`. `<main>` has no children in the frame's template, so the frame never touches what is inside it. The sign-in screen (`ui/SignedOut.vue`, `showSignedOut`) and the boot error replace `#app` wholesale and unmount the frame first.

A delegated handler that a legacy page still uses stays in `events/` even when a component shows the same control, and the component then has no handler of its own for it (both would run): `data-new-save` (the wizard), `data-save-note` (plan and backup notes, dialogs), `data-check` (every checklist), and `data-factory` / `data-calc-factory` (a plan step's "Open factory" button, factory cards, dialogs). The storage page still draws its own checklists with `taskHtml` in `tasks.js`; those steps have no edit tools, since step edits apply only to the build plan. Remove each one, and handle it in the components, when its last legacy user is converted.

Rules for components: keep class names and structure identical to the markup they replace, so `style.css` needs no change and the rendered layout can be compared with the previous release element by element; keep every `id`, `data-*` hook and form field name that `browser-check.mjs`, the tests or remaining delegated handlers use; move a control's handler into the component (`@click`, `@change`) and delete its delegated branch in `events/` in the same change; never use `v-html` for user text. Template asset URLs are page-relative (`./favicon.svg`), so `vite.config.mjs` turns off Vue's asset URL rewriting, and it keeps template whitespace as written (`whitespace: 'preserve'`): Vue's default removes a line break between two inline elements, which is the gap between buttons in a row. Test components with Vitest in `tests/ui/`, mounted through `render()` as the app mounts them, including a hostile name wherever user text appears.

## Functional inventory — retain these flows

- Create a named save; use the five-step settings/preferences/goals/resources/review wizard. Top step tabs are clickable, edits survive navigation, and Review recalculates when needed.
- The guided start: a new save opens on a short illustrated card sequence that writes the same settings object the wizard writes. "All settings" is offered on every guided screen and lands on the advanced step that owns the same question, keeping every answer; "Guided start" returns the same way. A save that already has profiles is asked what changed rather than every question again. Guided questions live in `preferences.js`; their artwork is either an item icon already bundled in `icons/` or inline SVG, never a new asset.
- Production you already run: from Phase 2 on the guided start asks for it as item + rate, and All settings step 1 carries the same control. Its item search is an in-page listbox, not a native `<datalist>`: that popup is browser chrome, so it cannot be themed or verified, and Chrome suppresses it entirely on an input with `autocomplete="off"`. Keep it keyboard-operable (arrows, Enter, Escape) and keep the half-finished rows in `wizard.supplyRows` — the editing rows are not the same as the rows handed to the planner, and picking a suggestion commits a name before any rate exists to go with it. It writes `settings.existingSupply`, which the planner credits; do not replace it with a checklist matched against the plan's own rows, which is what it deliberately is not. Review and the calculated resources page both report what was credited per phase. On Phase 1 the question is the HUB tutorial instead, which writes the existing `early-base-hub` and `unlock-…` keys through `newProfileState`; a profile created without either is the blank state earlier releases produced.
- Select, rename and remove profiles with confirmation. Switching profiles preserves each one's progress. The active-save header/footer must reflect the selected profile rather than the owner's original settings.
- View chronological guidance for Phases 1–5 and post-game, check tasks, record deliveries, save notes and manage custom tasks.
- Find/filter factories; inspect machine counts, rates, inputs, surplus, expansion and unlock guidance. Preserve the difference between original and calculated plans.
- View the selected storage contract, labeled container locations, floors and collectables/workshop guidance. Existing storage addresses matter to a physically built game layout.
- Preserve direct container Done checkboxes and room completion. Both write the same four existing `slot-<address>-<step>` keys; room completion skips unselected/reserved positions. Successful dialog note saves close only that dialog, and blank note saves remove the note key. Item icons are bundled in `icons/` with source attribution.
- Review resource budgets, feasibility, power headroom, transport allowance and fuel requirements. Resource tables show each ore's bundled icon beside its name.
- Work resource budgets out from node counts: a four-screen survey opened from All settings step 4 (`data-open-extraction`), asking miner mark and clock, then per-purity node counts per ore, then crude oil and nitrogen resource wells, then the total less what is already committed. It writes `settings.limits` and records the survey in `settings.extraction` so it can be reopened; the solver reads only `limits`, exactly as before. The counting screens carry the game's two World Randomization settings — the existing `distribution` and `purity` — and fill the counts from them via `presetCounts`/`presetSurvey`, by shifting nodes up or down the purity scale. `startingSurvey` seeds an unstarted survey from those settings; `matchingPreset` reports which world the counts currently are; `resetExtraction` (`data-node-reset`) empties every count while keeping the miner mark and clock, which are equipment and have no zero; it reads the form first and stashes the survey in `wizard.extractionUndo`, which `undoExtractionReset` (`data-node-undo`, rendered in the reset's place) restores and which a preset fill or `leaveExtraction` clears. It is deliberately not gated on `confirm()`: a browser that has been told to block this page's dialogs answers false without showing one, and the button silently does nothing — prefer an undo to a confirmation anywhere in this app. The VM harness in `tests/guided.test.mjs` records `document.addEventListener('click')` so `clickButton()` can press a delegated button for real; use it when adding one, because a handler that never fires otherwise passes every test. A test asserts each purity reproduces `resourceDefaults` for that setting to the item and that the node total never changes. `knownWorld(purity,distribution)` decides what can be filled: the default distribution for any known purity, and Random for the uniform purities only. Random is a shuffle — it moves which resource sits where, and their purities with it, but not how many nodes each resource has — so under a uniform purity the totals are exactly the default map's, and under a split-keeping purity the totals are right while the split is not. Resource wells are the exception: a well is randomized whole and the map's wells hold different numbers of satellites, so `presetSurvey(purity,base,distribution)` fills nitrogen only on the default distribution and `matchingPreset` identifies a world by its ordinary nodes alone. Do not fill counts for the resource-rich distributions or a random purity: those are seed-dependent and no authoritative table exists. `richShape` says which way each rich distribution pushes the map, in words and deliberately without numbers, because direction is the only thing independent counts agree on; a test asserts it stays number-free. The yield table lives in `preferences.js` and is pinned by a test that rebuilds the shipped `DEFAULT_LIMITS` and `PURE_LIMITS` from the known node counts — do not change a rate there without that test agreeing.
- Edit the build plan per profile: reorder steps, rewrite titles/details, link steps to factories, remove and restore steps. Removed and renamed steps keep their checklist keys and completion.
- Group factories into named groups on both factories pages, including production splits where one item serves several groups (assignments keyed by factory/row id in `factoryGroups`). Removing groups must never touch factory progress.
- Duplicate a profile (full copy including progress) and share a profile (scoped transfer export without progress) from Saves & profiles.
- When adding a profile to an existing save, the Review step offers carrying that save's progress over: a source-profile picker and one checkbox per record group. It stays a five-step wizard, the source profile is never modified, and a brand new save shows no panel and starts empty.
- Export/import full saves in both editions. Preserve progress-only backups where currently supported. Import confirmation must explain whether it adds copies or replaces progress.
- In Docker, retain account setup/login/logout and user isolation. In browser mode, show local-storage and backup information instead of server/account claims.
- Retain error, loading, empty-workspace, infeasible-result and calculation-in-progress states. Never show a successful save after a failed write.

## Implementation constraints

An update must never break existing progress. A redesign that changes saved structures or task identifiers must implement and test the migration requirements in `../AGENTS.md` before release. Keeping old records in storage is insufficient if users can no longer see or use them. Preserve access to original plans and completion history, including where new steps cannot be mapped automatically.

The UI (`app.js` and the modules in `app/`) uses hash routes (`#plan`, `#factories`, `#storage`, `#resources`, `#backup`, `#profiles`, `#wizard`, `#account`) and delegated events. Preserve working deep links. Keep `data-*` action hooks and form field names compatible or update all handlers and tests together. Checklist IDs and saved data keys are not visual implementation details: keep them stable.

Use the shared request path and browser API adapter. Do not bypass them with localStorage, cookies, new server calls or hardcoded profile state. Keep calculation in the browser worker for the public version, and preserve transactional saves and explicit profile scope across tabs.

The public deployment is under `/satisfactory-planner/`, while Docker serves `/`. Use URLs that work in both environments. Update the build allowlist for new fonts, icons, scripts or images; never fix only `dist/`. Avoid external CDNs and trackers for ordinary presentation assets. Keep third-party licenses and asset attribution.

User-provided names, notes, tasks and imported values are untrusted text. Continue escaping them before HTML rendering. Build all markup with the `html` tag from `app/html.js`, which escapes every interpolated value; do not concatenate HTML strings or call `esc()` in a view. Nest markup as its own `html`, pass arrays instead of `.join('')`, guard numbers with a comparison (`${n > 0 && …}`, since `0` renders), and keep `raw()` for fixed markup such as the SVG glyph tables and attribute fragments, never for user text. Helpers return `Html` and take plain text: `header()`, `stat()`, `field()`, `option()`, `dialog()` and `inputText()` escape what they are given, so pass names as they are. Page-level `render*` functions and every `innerHTML` assignment use `String(html…)`, because `render()` and the tests expect plain strings. `tests/interface.test.mjs` renders every page, edit mode and dialog with a hostile name and fails on markup that is escaped twice or text that is not escaped at all; add new screens there. Use safe URL handling for imported links. Preserve keyboard operation, visible focus, labels, semantic buttons, dialog dismissal/focus handling and readable contrast. Tooltips must work without a mouse and must not be obscured by duplicate native `title` tooltips. Do not use `alt` as a tooltip substitute; meaningful image alt text still belongs on images.

Show MW below 1,000 MW and GW where appropriate above that. For machine instructions distinguish total machines, full-speed machines and any adjustable machine, with output rate alongside clock percentage. Honor calculated whole-machine/surplus settings instead of changing the math for visual neatness.

## Redesign verification

1. Read the existing UI and capture its functional inventory before replacing large sections.
2. Inspect both an original handbook and a newly calculated profile. Use isolated test data or imported copies; do not experiment on the owner's live workspace.
3. Run the root checks and browser integration test after functional changes. Add coverage for new behavior rather than assertions that merely repeat CSS markup.
4. Inspect the rendered result at desktop and narrow/mobile widths: navigation, long item names, resource tables, dialogs, wizard controls and tooltips must remain usable.
5. Verify keyboard navigation, fresh start, profile switching, reload persistence, failed/invalid import feedback and successful full-save transfer. Test both server mode and a rebuilt static subpath preview.
6. Check there are no browser errors, broken assets, clipped controls or misleading save indicators. A successful Node test is not visual QA.

Keep redesign changes focused on presentation unless the user requested planning changes. Document any deliberate behavior or architecture change in the handoff and update the root guide if necessary.
