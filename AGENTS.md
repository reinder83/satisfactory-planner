# Satisfactory Planner — agent guide

Read this file before changing the project. For interface work also read `public/AGENTS.md`. `README.md` summarizes the app for users; `docs/USER-GUIDE.md` describes the user features in detail, `docs/SELF-HOSTING.md` the Docker installation and `docs/DEVELOPMENT.md` running from source, tests, builds and deployment. These instructions describe the current implementation, not a requirement to keep its visual design. Follow the user's current request where it changes the scope.

## Product and priorities

This is a Satisfactory production planner and progress notebook, not a game-save parser. Users create named saves, configure game settings and goals, and track chronological construction steps per profile. There are two supported editions:

- Docker/Node: server persistence, optional accounts, multiple users and devices.
- GitHub Pages: static assets, browser-side calculator, IndexedDB persistence, no server or login.

Both editions must continue working. A design redesign is welcome; it must preserve existing saves and behavior. Do not replace the functional application with a demo, hardcoded dashboard, or mock data.

Terms (#1046): what the code and these guides call a factory group (`factoryGroups`, `fg-*` ids, `#factories/<group>/flow`) is a **factory** to the user, and a calculated row (a recipe line of the plan, with its `calc-<phase>-<row id>` check) is a **production line**, "line" in counts and short labels. Everything a user reads (labels, headings, notices, errors, ADA, step texts, `README.md`, `docs/`) uses those words, never "group" for a factory or "factory" for a single line; code identifiers, saved data, routes and keys keep their names. See "Wording" in `public/AGENTS.md`.

## Data compatibility is essential

**Mandatory release rule: an update must never lose, reset, orphan or incorrectly reassign a user's progress.** This applies to major redesigns, rewritten components, changed task identifiers, schema changes and both persistence editions. Existing users must be able to migrate to the new version without recreating saves or manually re-entering progress. A release is not ready until its migration path is implemented and verified.

- Support upgrades from every previously released data format, directly or through a tested migration chain. Do not assume users installed every intermediate release. Version persisted data explicitly when its structure changes.
- Migrate profiles, calculation snapshots/handbooks, checks, notes, delivery counts, custom tasks and active selections together. Preserve server ownership and browser-local isolation.
- For renamed, split, merged or removed steps, define explicit identifier mappings. Preserve original completion records when no unambiguous mapping exists and expose them for review; do not silently discard them or mark unrelated new work complete. Keep the original saved plan accessible when a replacement changes its meaning.
- Perform migrations atomically and make retries safe. Retain a recoverable copy of the pre-migration data before modifying it. Failed migrations must leave that data intact and present recovery guidance, never silently initialize an empty save. Automatic updates must not depend on the user having remembered to export a backup.
- Apply equivalent safeguards to IndexedDB and server files. Keep older full-save exports importable through the same version-aware migration path. Never downgrade or overwrite an unknown newer format; explain that a compatible app version is needed.
- Add anonymized fixtures for released formats and test direct/skipped-version upgrades, repeat attempts, partial-failure recovery and old exports. Verify exact progress and ownership preservation, not just that the new application opens. Migration tests are required whenever compatibility is affected.

- One deliberate exception, by the owner's decision (#51): removing an added storage bay also deletes the `slot-<address>` checks and notes of that bay's addresses, so a bay that later reuses the letter starts clean. The confirm dialog says so. The printed room's own bays (A–R, `STORAGE_ROOM` in `public/storage-room.ts`; `handbookBay` in `public/state.ts` keeps its old name) cannot be removed, only hidden (`storageBayHide`), which keeps all their records until they are restored; an added bay may take a printed bay's letter only while that printed bay is hidden and only with `replace`, after the user confirms: that clears the hidden bay's kept records first, the same exception (#167). One stored before these rules, sharing a letter with a printed bay still in the room, is removed without touching the printed bay's names or records. Records already orphaned by an earlier removal are left alone, because a reused letter makes their owner unknowable. Everywhere else the rule above holds.
- Ownership hierarchy: server user → named save → profile. Each profile owns its checks, notes, deliveries, selected phase and custom tasks. A user's stored active save and each save's active profile mean what the user opened last, which a new tab opens; each open tab keeps its own save and profile across reloads and writes only to it (#1052, view state in the tab's sessionStorage, never stored; see `public/AGENTS.md`), so the stored shape is the one every release has read. The phase a tab shows is view state too, in the tab's memory (#1053): the phase picker only shows a phase, and the saved working phase (`settings.phase`) changes only through an explicit action ("Work on Phase N", the build plan's "Go to Phase N+1", a milestone-only working phase's "Go to Phase N"), so nothing new is stored.
- A new profile added to an existing save may start from a chosen sibling profile's records (`newProfileState` in `public/state.ts`, used by both editions). It copies, never moves: the source profile is untouched. World-shaped records (unlocks, the storage room, commissioning steps, deliveries, notes) copy as they are; plan-shaped `calc-` checks copy only where the new plan needs no more machines and no more input, and are carried unticked for review otherwise, matching `/api/round-up`, except a grown line (#1174, `carryLines` in `public/state/carry.ts`): the same row with more machines, not split by lines made on site, is carried unticked with the machines it had kept in `builtMachines` (`{ 'calc-<phase>-<row id>': count }`, state version 19, below), counted in `grownCount` rather than `reviewCount` (both editions' replies and toasts say so). A line the source left unticked with a count keeps it while the new plan still needs more; once the new plan needs no more than stand, it comes out ticked, all its machines standing (#1181, `keepStanding`), never dropped. The build plan reads it beside the stored plan (`public/app/built-lines.ts`, `grownLine` in `app/views/calculated.ts`), only while the step is unticked and the plan needs more than stand: the step says "5 of 6 built" under its title and opens with a table of the machines and inputs built, needed and to add ("5 Refineries built, so add 1, which takes …", `builtSoAdd` in `public/progression.ts`, the generator steps' wording), with the line's text under it; "Built so far" runs the line at the share its built machines make (`grownShares`), its card on the Factories page says "5 of 6 machines built: add 1" (◑ Partly built), and ADA has the calm `grown-lines` line. Ticking the step means all its machines stand; the count stays, so an untick reads "5 of 6 built" again, and the next carry counts from the ticked line's machines. Shrunk, switched and removed lines (#1175, `public/state/built-match.ts`, the same field, no new version): `standingLines` counts the machines on each of the source's lines (a ticked line its machines, or more where a carry kept spare ones; an unticked one its own count; a line its plan no longer has its kept count, until the switch below is done). A ticked line that now needs fewer machines than stand stays ticked and keeps them (its step says "6 built, 1 spare" under the title, ticked or not, `data-step-spare`, and a table of the machines built, needed and spare, "Switch it off or dismantle it, or underclock all 6 to share the work", never to build them). A line with machines standing but no tick (a grown line partly built, a line an earlier plan had left that this one has again) comes out ticked when they are at least what the plan needs, keeping any beyond it as spare, and keeps its count unticked otherwise (`keepStanding`, #1181); so does a ticked line the new plan grows back to no more than stand. A user's untick of a line with spare machines makes its step say to tick it again once they run. A built line the new plan no longer has, in a phase it builds (`carryFormerLines`, after `keepSiteTicks`), keeps its machines under its own key: when a line of that phase not ticked makes the same main product (`successorOf`: its first output, a generator's `power:<machine>`; the same machine first, then plan order), the key is left unticked and that line's step is an adjust task naming both recipes, with a table of the lines, machines built, needed and the change ("Switch 4 Constructors from Screws to Cast Screws, and add 1"; another machine is "… replaces …: the 4 Constructors built for Iron Plate can be dismantled or kept"; any left over are spare; `builtLineChanges` in `app/built-lines.ts`), its card "4 to switch from Screws, 1 to add" with the ◑ To switch chip; once every line making that product is ticked the switch is done and nothing shows, and the next carry drops the count. Otherwise the key stays ticked and the build plan lists it over the steps as no longer needed, "can be dismantled or kept" (`ui/plan/FormerLines.vue`, `data-former-lines`), never a silent drop; a line coming back in a later plan gets its count back, unticked. What such a line was is read from a row with its id in any phase of the plans at hand, else from the catalog's recipes and generator lines (`recipeBook`, `catalog().generatorLines`; both editions pass it to the carry, `recipeBookData` in `server/scope.ts`); without it, a line is named by its id and kept as no longer needed. Both editions' replies and toasts count these in `changedCount`, and ADA has the calm `changed-lines` line. Whether keeping the built recipe saves enough to skip a switch needs the solver and is #1176 (built-aware solving); round-up copies the field as it copies all progress. Creating a profile without `carryFrom` must keep producing the blank state earlier releases produced. The finished work a new profile may start with (`built`, `builtKeys` in `public/state/carry.ts`) is a production row of its plan, an `early-base-` step or an unlock: `unlock-`, `recipe-unlock-` and `hard-drives-<phase>` (#1068, the wizard's "What you already have"); anything else is dropped, and carried records still win.
- Calculated profiles retain calculation snapshots. Do not silently recalculate existing profiles during startup, navigation, import, or an application update.
- Create profile stores the plan the wizard's Review showed (#1060): `POST /api/preview` keeps its plan in memory for the exact settings it was sent (`reviewedPlans` in `public/reviewed-plans.ts`; per user on the Docker server, per tab in the browser edition; never a live estimate, `?estimate=1`; the newest eight, for an hour), and `POST /api/profiles` with those exact settings stores a copy of it instead of calculating again. Any other settings (changed after Review was drawn, another tab) are calculated afresh, so the stored plan is always what `calculate()` gives for its settings (tested against a fresh calculation, both editions, `tests/reviewed-plans.test.ts`). Edit settings' "Recalculate in place" (`POST /api/recalculate`, #1138) stores Review's plan the same way, but only one Review calculated after the profile's plan was made (`reviewedReplacement`, comparing it with the request's `planCreatedAt`), so a recalculation never brings back a creation time the profile had and the stale-tab refusals (409) work as before; the plan's recalculation offers have no Review and calculate. Nothing new is stored.
- Edit settings recalculates a profile in place only when the user presses "Recalculate in place" (`POST /api/recalculate`, both editions, #1071): the profile keeps its id and gets the new plan, name and the progress `calculatedProfile` carries from itself (`recalculatedProfile` in `public/state/carry.ts`, the carry rules and picks of a new profile carried from it). Unlike a new profile, which starts from the world facts only, it also keeps (#1112) the phase worked on (`inPlacePhase`: raised to the new start phase only when the edit moved the start phase past it; a milestone-only phase the user was on stays unless the plan has a guide) and the record of every other step the new plan still lists under the same id, over all its phases (`keepListedSteps`, `phaseSteps` with progression.json, which both editions pass): `space-elevator`, `mining-`, `retire-`, `deliver-<phase>`, `alien-power-augmenter`, `sloop-hand-fed`, `calc-<phase>-storage` and a guide's own steps. Production lines keep their review rule and keys the carry options copy by prefix follow the picks; a step the new plan no longer lists is not copied (the backup keeps it). The revision is moved past the previous one so a stale whole-value write from another tab is refused. The previous version is kept whole (plan, progress, payoff) as an ordinary profile named "<name> (before edit, <date>)" right after it, so nothing is deleted, linked to it by the optional profile field `backupOf` (the profile's id; absent from every other profile and from every profile stored before it): older releases keep it in their stores without reading it, and their imports leave it out (`validateTransfer` rebuilds each profile), so they read the backup as any profile. "Restore this version…" in the backup card's ⋯ menu (`POST /api/restore-version`, both editions, scoped to the backup; `checkRestore` and `restoredVersions` in `public/state/restore.ts`) swaps the two versions' contents after a confirmation that names both profiles: the profile keeps its id, name, place and own link and gets the backup's plan, progress and payoff, and the backup's place gets the replaced version under "<name> (before restore, <date>)", still linked, so the restore is undone the same way; no profile is added or deleted, both revisions move past either one's, and a request naming a plan either profile no longer has is refused (409). A link only counts while it names another profile of the same save (`restoreTarget`; the summary sends it as `backupOf` with each profile's `planCreatedAt`): a full export keeps it, an import remaps it to the new ids (`remapImportedIds`), a one-profile export or share and `validateTransfer` drop one whose profile is not there, and Duplicate leaves it behind. A backup kept before the link has none, so it offers no restore (tested in `tests/restore-version.test.ts`). The request names the plan the edit started from (`planCreatedAt`); a profile recalculated since is refused (409), and a save without room for the backup (30 profiles) is refused; both write nothing. The plan's own recalculation offers ("Recalculate in place with exact clocks", "… with items made on site", "… with transport fuel" and "… with what you have" (#1068), `recalculateOffer` in `public/app/ui/recalc-offer.ts`) send the same request (`postRecalculation` in `public/app/recalculate.ts`): the plan's settings with the offer's change, the profile's own name and every carry pick (as the new profile they made before was carried), only after a confirmation that names the backup, and a 409 opens the plan the profile has now. "Round up production" still makes a new profile (`/api/round-up`, which copies all progress rather than carrying it).
- A profile created before #1105 without a typed name carries its goal's name alone ("Balanced progression"). No migration renames it: its card on Saves & profiles offers the descriptive name (#1071, see `public/AGENTS.md`), and only the user's "Rename to …" renames it, through `/api/rename`. Dismissing the offer stores the optional profile field `renameOfferDismissed` (`true` or absent; `POST /api/dismiss-rename-offer`, both editions; `public/state/rename-offer.ts`), so the offer does not come back. It is no progress and needs no state version: it is absent from every profile stored before it and from every profile whose offer was never dismissed, older releases keep it in their stores without reading it and leave it out of what they import (`validateTransfer` rebuilds each profile), which only brings the offer back. The summary, every export (a one-profile export and a share too), every import and `validateTransfer` keep it (any other value is left out, not refused); a recalculation in place and a restore keep it with the profile that keeps the name, and Duplicate, a recalculation's backup and the version a restore replaces, which get names of their own, leave it behind (tested in `tests/rename-offer.test.ts`).
- Items made on site (#868, #875): a factory group that marks an item (`factoryGroups.local`) gets its own whole-machine line for it in a recalculation the user starts, sized to that group's own consumers, and a central line covers the rest. The planner reads the groups only through the optional setting `settings.onSite` (`{ [groupId]: { name, items, shares: { [phase]: { [rowId]: share } } } }`), worked out by `onSiteSettings` in `public/app/on-site.ts` when the recalculation starts and frozen in `plan.settings` like `transportFuel`; the marks are set with the Factories page's "Made on site" picker (`factoryLocal` update, #877), and a changed mark only makes the page offer "Recalculate in place with items made on site" (the profile recalculated in place, progress carried, its previous version kept as a backup, #1071; see `public/AGENTS.md`), never a recalculation by itself; it is absent from every plan without it, which therefore calculates exactly as before (tested). A consumer row split over several groups is attributed by `rowShares`, measured against that row's total in the same phase of the plan being recalculated: fixed rates first, then the null-rate memberships split the rest; a row that plan lacks in that phase has a share only for its null-rate memberships, split evenly, and its fixed-rate parts count only where the recalculated plan builds it (`ifBuilt`, #1038, below). Shares and fixed-rate parts are per row id, as memberships are (#904): an amplified line (`amp:X`) and its unamplified twin (`X`) are separate rows everywhere, each with its own memberships, card and check key, and a recalculation carries memberships by the exact id (`mergeGroups` in `public/state/carry.ts`). So the planner reads a group's share (`shareOf`) and part (`phaseRate`) of a row by the row's own id only, with no fallback from one twin to the other either way, as `rowPlaces` places the row in the books: a group's line is never drawn on for a twin the books do not credit it with, and a twin only another group holds draws on that group's line alone. A group that holds only a recipe's amplified twin still gets its copy of the recipe making the item, because only the inner fit's pool holds the twins (`siteCopies`). In the solver (`planner/on-site.ts`) each such group gets a copy of each recipe whose main product is the item (its first output, `primaryOutput` in `planner/recipes.ts`; a recipe that makes it only as a byproduct, such as Rocket Fuel for Compacted Coal, stays central, because its copy would run the whole recipe and take over the group's own consumer, #1012), feeding a balance of its own (`item:<item>@<group>`, internal to the solve); the group's share of each consumer draws from it and the rest from the central balance, and a copy takes the items its own group marks (Copper Ingot for its Wire line) from that group's lines. Other inputs, byproducts, raw resources, existing supply and every demand stay central, except that the central byproduct of a marked item that balances exactly (a fluid such as Dark Matter Residue, which the Space Elevator part lines make) feeds the group's balance first (#1012, the owner's decision there; `siteFeeds` in `planner/on-site.ts`): a route `byproduct:<item>@<group>` from the central balance into the group's, a phase's routes of the item together capped by what the central lines make of it as a byproduct (`byproducts:<item>`), and preferred over the group's own line by a cost just below nothing (`BYPRODUCT_FIRST`, a tenth of a raw unit's), since both cost the same machines. So the group's line makes only the rest, and none when the byproduct covers the group's need: then no line is built, and the heading words the mark "(a byproduct of central lines covers it)" with no notice, because a recalculation plans it the same way; a mark of an item the phase makes only as a central byproduct (Heavy Oil Residue beside Plastic and Rubber), which never gets a line, reads the same (`BYPRODUCT_NOTE`, `markNote` in `public/app/on-site-picker.ts`, #1027 review). A solid byproduct has the sink and gets no route, so its group's line makes all the group uses, as before, and a phase without such a byproduct builds exactly the model it built before. The books need nothing new: the group's demand its own lines do not meet stays in `demand` and draws on the central supply, so the Logistics page shows the byproduct going into the group, and the plan's on-site warning adds a sentence per such item ("Central lines also make Dark Matter Residue as a byproduct, which cannot go to the sink: it goes to Gamma first, and Gamma's own line makes only the rest."). Copies are whole machines under `wholeMachines`, never amplified, not made for nuclear recipes, and a group with no consumer of the item in a phase gets no line there. A per-group line's row id is `<recipeId>:<groupId>` with `onSite: { group, recipe }` (`safeKey` allows `:`, not `@`, so its check key `calc-<phase>-<rowId>` is accepted by released versions), and its unlock and milestone are the recipe's (`recipeIdOf` in `public/progression.ts`). Such a line belongs wholly to its group while the group exists (`rowMemberships` in `public/app/group-order.ts`, which `rowPlaces`, `homeGroup` and `membershipsOf` in `app/views/factories.ts` go through; a saved assignment for its id counts only once the group is removed), so its card, its share and its build-plan step sit with that group; the step is titled "<item> for <group>" (`rowStepTitle`), and in the build order it feeds only rows with a share in its group (`sitesFeed`). On the Logistics page's books (`itemBooks`), its supply of an item the plan was calculated to make on site for its group (that group's `items` in the plan's `settings.onSite`, as the solver routes them: `siteItems` in `public/app/group-links.ts`, #1003) meets that group's own demand first and stays inside the group; what it makes beyond that goes to the sink (`sunk`), never to another group, so groups that make the same item on site have no link for it between them (#876). Any other output of the line is ordinary supply, as a central line's of the recipe: Water from its Aluminum Scrap line though the group marks Water (a raw resource the recalculation left out), or an item marked since. A mark cleared since changes nothing either, so the books, the flow page and the dialog describe the plan as it was calculated until a recalculation. The pages pass the plan's `settings.onSite`; without it (no plan has such lines without it) the group's marks stand in, as before. A group edit after the recalculation can leave the group asking for less than its line was sized to (#918): the sink still takes only the plan's surplus of the item, from each group in proportion to its excess, and the rest is `offered`, ordinary supply at the group that the other places share, so the books, the flow page and the factory dialog keep balancing without a recalculation (no notice asks for one); groups as the plan was calculated for offer nothing and come out exactly as before (tested against a recording), fixed-rate memberships included (#984, below), except for an item that balances exactly (a fluid) whose row with a fixed-rate membership changed its total in the recalculation. An own line's dialog note then says its group asks for less than it makes and where the rest goes, or that it asks for none and the sink takes all of it (#1002); it speaks of "the factory's other lines" only when the group has another own line for the item made on site for it, never for a byproduct, which a sentence of its own sends to the whole plan's demand (#1001). Any other line's note names the groups whose leftover meets part of the demand its rates leave out, and says "the other lines making it" rather than "the other recipes" when one of them copies its recipe (#1002). The factory dialog's flow (`calcFlowModel` in `public/app/flow.ts`) reads the same books for such an item (#956): a consumer's input links to the single line that gives it the most of the item, compared line by line (`inputSource`, #972; plan-wide, the line making the most, as the lines share a demand in proportion to what they make; on a tie a group's own line first, then the phase's order), its deliveries and spare-belt suggestions name each line as its build-plan step (`rowStepTitle`: "Wire for Alpha", #964), a group's own line delivers only to its group's share of each consumer and its excess to the sink, and the other lines making the item leave out what the own lines give; a phase without such a line reads no groups and draws exactly as before (tested). A recalculation that carries factory progress (`newProfileState`: in place, or into a new profile) cannot carry two kinds of tick onto one line: a ticked central line whose phase gains a group line of its recipe the source plan lacked, and a ticked group line the new plan no longer has (`siteTicksForReview`). Those are kept exactly in `onSiteReview.checks` (state version 15) and listed on the Notes page (`ui/notes/SiteReview.vue`, with ADA's `site-review` line); a central line among them that the new plan still has is unticked for review (counted in `reviewCount`), and the group lines start unticked. ## Planning rules to preserve

Keep presentation separate from calculation. Do not change recipe rates, power budgets, goals or resource assumptions to make cards look cleaner.

- A profile is built for the phase it records in its settings. Do not offer or generate production for earlier phases (production lines, storage, power, hard drives, retirements): the user has already passed them, and each phase plan is a self-contained steady state that reads nothing from an earlier phase’s layout. A calculated profile still offers the phases before its start phase as milestone-only phases, listing only the milestones that belong there (the owner's answer on #570, #759: `milestoneOnlyPhase` in `public/progression.ts`, `firstPhase` and `milestoneOnly` in `public/app/session.ts`). The planner solves those stages too, but `calcStage()` reads none of them, so no page shows their production; a plan guide has no such phases.
- Where a phase stops using a line an earlier phase built, say so as a step: its budgets no longer include it, and a replacement is usually a different machine rather than an upgrade in place. Retire each line once, in the phase straight after the last one that needed it, and never one the plan picks up again later.
- Guidance must respect phase and milestone availability: early construction materials and biomass before later fuels, hard drives for alternates, relevant MAM unlocks, then later power and drone fuel upgrades. Each milestone a planned phase needs is one step, listed under its own phase (`milestonesListedIn` in `public/progression.ts`, #758): a HUB milestone under its tier's phase and a MAM node under the phase its costs first become available, a phase before the start phase included (#759). Every planned phase needs HUB Upgrade 6, Obstacle Clearing and Logistics Mk.2, because the biomass start-up steps and "Power available now" ask for them until a power unlock is ticked, so a profile made for a later phase lists them in Phase 1 (#781). Coal Power is needed from Phase 2 and Petroleum Power from Phase 3 whether or not the plan builds their generators (#1048), so a player who already runs them can tick them. "Power available now" never advises a power source below the one the player has ticked or the phase plans (#1048): with spare existing power in the settings (`availablePowerGW`), or Phase 5's Alien Power Augmenters, it says what the phase needs beyond that, from the stage's `requiredMW`, and the generation the plan builds for it (`generationMW` with the augmenters' boost, highest source first; the augmenters' own part is `availableMW` less that and the spare power, as `stageSupply` splits it, #1050 review) with what is left over and why (whole plants, Phase 5's waste-chain period, or the profile's minimum of uranium reactors), or that the spare power covers the phase; and the biomass start-up steps, and "Unlock Coal Power" unless the phase builds coal generators, are not listed then. A profile with Alien Power Augmenters needs the MAM node Power Augmenter, which Phase 5's augmenter step asks for: the augmenters are buildings, not rows, so the settings bring it in (#810). Its check key is `unlock-<id>` whichever phase lists it. Each alternate recipe a planned phase uses is likewise one unlock step, `recipe-unlock-<recipe>`, listed in the first planned phase (from the start phase on) whose lines use it (`hardDriveTasks`, #870), so ticking it never makes a later phase look started. The start-up steps that are done once in the game are listed once too (#872), with the check keys they always had: "Turn leaves and wood into Biomass" and "Unlock Obstacle Clearing, then automate Solid Biofuel" (`startup-biomass`, `startup-solid-biofuel`, `biomassStartupTasks`) only in the start phase, and "Unlock Coal Power before switching to coal" (`startup-coal-unlock`, `generationTasks`) only in the first planned phase from Phase 2 on (Phase 2 for a profile made for Phase 1, otherwise the start phase). Post-game plans Phase 5's stage, so a profile made for Phase 5 lists them in post-game too. The burner bank step is sized for its phase's load and keyed per phase (`startup-burner-bank-<phase>`), so every phase with the start-up keeps its own. A row's recipe is always `recipeIdOf` in `public/progression.ts`, never its row id: an amplified twin (`amp:<recipe>`) and a group's own line (`<recipe>:<group>`) share their recipe's unlock step, its title ("Unlock <recipe>", without "(somersloop amplified)") and its milestones, and so do the unlocks a new profile's picked alternates tick (`pickedRecipeUnlocks`) and the wizard's "Planner's choice" (`alternatesUsed`) (#901). Anything new that reads a recipe from a row goes through it.

- Random node randomization is a shuffle, not a regeneration: node locations never move, each location keeps its own purity rating, and only the ore assigned to it changes. Each resource therefore keeps exactly its default node count while its split across impure/normal/pure is drawn from the map's fixed pool of purity slots. So under Random the counts stay knowable for the uniform purities, where the split does not matter, and only the split is lost for the ones that keep the map's own (Default, Mostly Pure, Mostly Impure) — do not estimate that split, it is seed-dependent and observed to be biased per resource. The resource-rich distributions do change per-resource counts, by seed-dependent amounts, and have no authoritative table — community counts of those vary seed to seed, so treat any published table for them as one seed's reading.

## ADA

`public/ada.ts` holds ADA’s remarks: facts in, ordered plain-text lines out. `adaFacts` in `public/app/ada-panel.ts` builds those facts from the same counters the pages render, and escapes the text like any other untrusted name.

**When you add a feature, add ADA’s lines for it in the same change.** A new counter, warning, page or editing mode that ADA cannot see is a gap users notice. Give the rule a stable `id`, an `on` page affinity, a `tone` (`calm`, `warn` or `praise`), `lead: true` only for a state that makes everything else irrelevant (it ranks first), and cover it in `tests/ada.test.ts`.

Keep the deal the feature rests on: the joke is in the tone, never in the numbers. A remark may only restate what the plan already contains — including repeating the planner’s own infeasibility reason rather than inventing one — must never imply the app has altered saved progress, and must not be the only place some piece of guidance appears. Rules are skipped rather than thrown from, and the panel is wrapped in a guard: ADA must not be able to break the shell.

## Development and verification

Run commands from this repository root. Node 24 is used in CI; the package supports Node >=22.18 (the first 22.x that strips TypeScript types without a flag). The frontend was migrated to Vue 3 in stages, now all done; see "Vue migration" in `public/AGENTS.md`. Source files stay readable: `npm start` serves `public/` unbuilt, compiling the `.vue` files through Vite in middleware mode (see `devFrontend` in `server.ts`) unless `NODE_ENV=production`, and only `build.ts` minifies, for publishing.

```sh
npm ci
node server.ts
npm run check
npm run typecheck
npm test
npm run build
```

`npm run check` is Prettier; run `npm run format` rather than hand-compacting code. `npm run typecheck` is `vue-tsc --noEmit` (see "TypeScript" below). `npm test` runs `node --test` on `tests/*.test.ts` and then Vitest on the component tests in `tests/ui/`; it needs `npm ci`. The VM-based interface tests load the `public/app/` modules through `tests/helpers/app-source.ts`, which concatenates them in ES evaluation order: top-level names must stay unique across those modules, and a module changes another module's `let` only through that module's exported setter. The harness leaves out the Vue layer (`vue` and `public/app/ui/`), follows its imports of plain modules, and replaces the names plain modules import from it with do-nothing functions. It strips the types from a `.ts` module first (`stripTypeScriptTypes` from `node:module`), which leaves the rest of the text as written.

The component tests in `tests/ui/` import `node:assert/strict` as usual, but `vite.config.ts` points that import at `tests/ui/assert.ts` (#287). Plain `node:assert` prints both sides of a failed check at depth 1000, and a happy-dom element reaches the whole document and window, so a failed `assert.equal(document.activeElement, $('#x'))` or `assert.equal($('#x'), null)` hung for minutes and then crashed the Vitest worker. The wrapper's `equal`/`strictEqual`/`notEqual`/`notStrictEqual` report a DOM node by a short name such as `<button#save.primary[data-confirm-ok]>`; everything else is node:assert's. Compare page elements only with those identity checks: not with `deepEqual`, which still prints the whole node (compare an `id`, text or attribute instead).

### Structure

Keep each function about one thing and each module about one concern, so a change touches one small piece and a reviewer can follow it (#504). Long functions and catch-all modules are being split in sub-tasks of #504; new and changed code follows these rules now:

- A function that grows past about 60 lines, or nests blocks more than three deep, is split before more is added to it: pull each step out into a named function that says what it does, and keep the original as the short list of those steps. Prefer extracting over growing a function.
- A dispatcher over many cases (an HTTP route, an update `type`, a wizard step) is a lookup from the case to one named handler, not an `if`/`else` chain holding every handler's body. `mutate` in `public/state/mutate.ts` is the pattern: `stateEditFor` looks an update up in `recordEdits` or hands it to its family, and `mutateLayout` there looks a storage update up in `layoutEdits`, a table of one function per storage update type.
- One concern per module. A module that validates saved data should not also hold page text or seed data; when a module mixes them, move one out rather than adding a third. A new root script in `public/` is listed in `build.ts` (see "TypeScript").
- The two editions share logic instead of copying it. A rule both the server (`workspace.ts` and its handlers in `server/`) and the browser edition (`public/browser-api.ts`) apply, such as which checks a new profile carries, lives once in a shared module (`public/state.ts`, `public/transfer.ts`) and both call it; only transport, storage and error reporting stay per edition. Fixing a copy in one edition and not the other is how the editions drift apart.
- Repeated blocks become one helper with a name, when they mean the same thing (not merely look alike). Delete dead code rather than commenting it out; git keeps the history.
- A structural refactor is a pure refactor: no change to behaviour, error messages, saved data, request and response shapes or the interface. Existing tests pass unchanged, and an extracted unit that was hard to reach before gets its own focused test.

### TypeScript

All code is TypeScript. It moved one module at a time, in stages like the Vue migration: (1) the tooling, with `public/app/format.ts`, `ui/ItemIcon.vue` and `ui/StatTile.vue` as the first typed files (done); (2) types for the saved progress state (`state.ts`, every version), the legacy handbook, the calculated plan and the workspace, in `public/types/` (done); (3) the plain modules in `public/`, in two pull requests: (a) everything under `public/app/`, which Vite bundles (done), then (b) the shared scripts at the root of `public/`, which the server imports too and `build.ts` ships as separate files (done); (4) the components (done); (5) the server, `workspace.ts`, `planner.ts`, `optimizer.ts` and `docker-start.ts`; (6) the build tooling (`build.ts`, `browser-check.ts`, `vite.config.ts`) and the tests. Each stage was its own pull request and left both editions working. No JavaScript is left in the repository: the solver (`highs`) and the typefaces (`@fontsource/*`) come from npm, pinned in `package.json`, and `highs` ships its own types. `highs` is the one runtime dependency, which the Docker image installs with `npm ci --omit=dev`; everything else is a dev dependency.

Nothing compiles TypeScript to files: Vite and Vitest strip the types when they serve, test or bundle the code, esbuild when `build.ts` minifies, and Node 24 itself when it runs a `.ts` file. `tsconfig.json` only drives the type check (`npm run typecheck`, also in CI), with `strict`, `noUncheckedIndexedAccess` and `noUnusedLocals` on (an import or local nothing reads fails the check; delete it rather than silencing it). Rules:

- Use only syntax Node can erase (`erasableSyntaxOnly`): no `enum`, `namespace` or constructor parameter properties. Use a union of string literals or an `as const` object instead of an enum.
- Import a TypeScript module by its `.ts` file name (`'./format.ts'`), as Node requires; import types with `import type` (`verbatimModuleSyntax`).
- No `any`, no double cast (`as unknown as X`) and no `@ts-ignore`. The one double cast is in `tests/types/fixtures.ts`, for a JSON import, and says why; `tests/double-casts.test.ts` fails on any other, in any form (bracketed, broken over lines or with angle brackets). The node tests read the frozen handbook (`migrations/handbook-2026-09-13.json`) and `recipes.json` typed from `tests/helpers/data.ts`, the component tests from `tests/ui/setup.ts`, rather than casting a JSON import. A value from outside (saved data, a request body, an import, JSON) is `unknown` until a check narrows it; keep the run-time checks for those even where the types look sure. A single `as` is for a value a comment can vouch for (a form field whose options are the allowed values, a partial test fixture). `@ts-expect-error` only where code deliberately passes a wrong type, as a test of rejected input does.
- Types describe the code; they never change saved data. The data types live in `public/types/` (types only, left out of both builds; import them from `public/types/index.ts`). Saved data has two shapes there: `ProgressState` is what `validateState` returns and `SavedState` any released version it accepts; `CurrentCalculatedPlan` is what `calculate()` returns today and `StoredCalculatedPlan` any plan an earlier release froze on a profile, so a field added to the planner is required only in the Current types. Read saved data through the Stored types.
- `tests/types/data.types.ts` checks the types against the frozen migration handbook (`migrations/handbook-2026-09-13.json` against `Handbook`, the converter's input type) and a plan frozen by the first release's planner (`tests/fixtures/calculated-plan-2026-09-12.json`), both ways: the data must fit the types and hold no field they do not declare. `tests/types/fixtures.ts` has a typed state for every version, which `tests/data-types.test.ts` runs through `validateState` and `validateTransfer`. When the saved shape changes, add a fixture of the new shape and keep the old ones.
- The entry points that read or produce saved data (`validateState`, `mutate`, `initialState`, `newProfileState`, `shareState`, `calculate`, `settings`, `catalog`, `validateTransfer`) declare these types in their signatures. A type that does not resolve silently becomes `any`; `data.types.ts` pins each one, so keep it in step when changing a signature.
- Look up a page element the frame or the current screen always has with `required(selector)` (`app/format.ts`), which throws naming the selector; keep `$(selector)` and a null check for one that may be absent. Code that only runs while the wizard is open reads the draft through `draft()` (`app/session.ts`), which throws when there is none; code that may run without one reads `wizard` and checks it.
- A non-null assertion (`!`) needs a comment saying why the value is there (a filter just above, a loop bound), unless it is plain from the line itself.
- Every component is `<script setup lang="ts">` with type-based `defineProps<{ … }>()` (`withDefaults` for defaults), so vue-tsc also checks its template against those types. A prop takes a named type (`PlanStepView`, `FlowModel`, `StorageBayView`, …), never `Object` or `Array`; `GroupSections.vue` is generic (`generic="T"`) over the items it groups. Event handlers type their event (`e: Event`) and cast its target to the element they are bound on. An attribute a template drops is bound to `undefined` (DOM typings refuse `null`; Vue removes the attribute for both).
- Every script at the root of `public/` is TypeScript and ships as `.js`: `build.ts` strips and minifies each shared one (`SHARED`) with esbuild and rewrites its `./x.ts` and `../x.ts` imports to `.js`, and bundles `app.ts` (which `index.html` loads in development) into `app.js` (`BUNDLED`, with `app-root.ts`). A new root script must be added to `SHARED` or `BUNDLED` there; so must a new module in a shared folder (`SHARED_DIRS`: `public/state/` and `public/preferences/`), which ships under the same folder.
- The server imports the shared sources (`./public/state.ts`, `transfer.ts`, `handbook-migration.ts`, and `preferences.ts` through the modules of `planner/`) and Node runs them as they are. The Docker image therefore copies `public/*.ts`, `public/state/*.ts` and `public/preferences/*.ts` next to the built `public/` (a new shared folder needs its own `COPY` line), and `server.ts` answers 404 for any `.ts` path so browsers only ever get the built files. The Docker smoke test in CI starts that image, so a server import the image lacks fails there.
- The server-side modules (`server.ts`, `workspace.ts`, `server/`, `planner.ts`, `planner/`, `optimizer.ts`, `docker-start.ts`) run as they are in the Docker image, which copies each by name (the `Dockerfile` `COPY` lines): a new server file or folder is added there, or the image fails the smoke test. A request body is `unknown` until a check narrows it; keep the existing checks rather than trusting a cast. The Pages edition ships `planner.ts` as `planner.mjs`, each module of `planner/` as `planner/<name>.mjs` and `optimizer.ts` as `optimizer.mjs`: `build.ts` strips them (`plannerJs`), replaces a few snippets by exact match (in `planner/data.ts` only: the `node:fs` import, the `recipes.json` read; in `optimizer.ts` the `highs` import), and renames the planner's import paths with `plannerImport`, so keep those snippets unchanged.

### Naming

Name variables, parameters and helpers for what they hold, in words a reader understands without looking up where they came from (#503): `user`, `profile`, `draft`, `entry`, `checkKey`, not `u`, `p`, `d`, `v`, `k`. Rules:

- A single letter only for a counted loop index (`for (let i = 0; i < rows.length; i++)`) and for the parameter of a one-line callback whose collection says what it is (`saves.filter(s => s.userId === user.id)`, `profiles.find(p => p.id === profileId)`). A callback that spans several lines, or whose parameter is not an item of the collection it is called on, gets a full name: `commit(draft => { … })`, `users.find(account => account.id === userId)`.
- No private abbreviations: `error`, not `e`, in a `catch` or error callback; `phase`, not `ph`; `input`, not `b`, for a request body. Names every Node or DOM example uses (`req`, `res`, `url`, `id`, `el` for an element) may stay.
- A rename is a pure refactor: it never renames what leaves the code (JSON keys, saved state fields, request fields, `data-*` hooks, form field names, exported names other modules or tests import). Keep comments in step with the new name.
- Existing code is being renamed area by area in sub-tasks of #503; new and changed code follows these rules now.

The server defaults to port 8080. Set `HOST=127.0.0.1` for a local-only preview and `DATA_DIR` to an isolated temporary folder for experiments. Environment-variable syntax differs by shell. Check whether an existing server is running before starting another; never terminate unrelated processes.

For real-browser verification, Playwright is a pinned dev dependency (`npm ci` installs it, without a browser); CI then downloads Chromium:

```sh
npx playwright install --with-deps chromium
npm run build
node browser-check.ts
```

`PLANNER_PLAYWRIGHT` can point to an already installed Playwright entry file. `PLANNER_BROWSER_CHANNEL=msedge` can use installed Edge. Browser checks serve the build under `/satisfactory-planner/`, run the actual WASM calculator, and test persistence, isolated profiles, concurrent tabs and Docker transfers in temporary storage.

Use tests appropriate to the change. UI redesigns require real-browser inspection in addition to tests; see `public/AGENTS.md`. The VM-based interface tests currently reference UI functions/selectors. If restructuring them, update the tests to cover equivalent behavior rather than deleting coverage. Documentation-only changes need link/path and diff review, not the whole Docker test suite.

- Public URL: `https://reinder83.github.io/satisfactory-planner/`.
- Docker image: `ghcr.io/reinder83/satisfactory-planner:latest` (AMD64 and ARM64).

Pushes to source `main` run checks and publish both editions. Pull requests run checks without deployment. The source workflow uses the repository-scoped `PAGES_DEPLOY_KEY` secret to push only built website files to the public site repository; its own Pages workflow deploys them. Do not replace this with a broad personal token. No live data, the frozen migration data in `migrations/`, account records or workspace files belong in the public build.

Frontend assets added during a redesign need entries in the Pages allowlist in `build.ts` and must be available in Docker too; a new script at the root of `public/` must be listed as shared or bundled there, or the build fails. Preserve subpath-safe URLs and worker/WASM loading. Do not add a backend dependency to the public edition. Preserve PUID/PGID/TZ, privilege dropping and data-volume compatibility in Docker.

Work in the source repository; direct edits to generated public-site files will be overwritten. Pushing `main` is a live release, so check the user's requested publishing scope. Report what changed, verification performed and any remaining limitation. Update these guides when architecture or commands change.
