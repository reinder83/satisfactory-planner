# Satisfactory Planner — agent guide

Read this file before changing the project. For interface work also read `public/AGENTS.md`. `README.md` summarizes the app for users; `docs/USER-GUIDE.md` describes the user features in detail, `docs/SELF-HOSTING.md` the Docker installation and `docs/DEVELOPMENT.md` running from source, tests, builds and deployment. These instructions describe the current implementation, not a requirement to keep its visual design. Follow the user's current request where it changes the scope.

## Product and priorities

This is a Satisfactory production planner and progress notebook, not a game-save parser. Users create named saves, configure game settings and goals, and track chronological construction steps per profile. There are two supported editions:

- Docker/Node: server persistence, optional accounts, multiple users and devices.
- GitHub Pages: static assets, browser-side calculator, IndexedDB persistence, no server or login.

Both editions must continue working. A design redesign is welcome; it must preserve existing saves and behavior. Do not replace the functional application with a demo, hardcoded dashboard, or mock data.

Terms (#1046): what the code and these guides call a factory group (`factoryGroups`, `fg-*` ids, `#factories/<group>/flow`) is a **factory** to the user, and a calculated row (a recipe line of the plan, with its `calc-<phase>-<row id>` check) is a **production line**, "line" in counts and short labels. Everything a user reads (labels, headings, notices, errors, ADA, step texts, `README.md`, `docs/`) uses those words, never "group" for a factory or "factory" for a single line; code identifiers, saved data, routes and keys keep their names. See "Wording" in `public/AGENTS.md`.

## Data compatibility is essential

**Mandatory release rule: an update must never lose, reset, orphan or incorrectly reassign a user's progress.** This applies to major redesigns, rewritten components, changed task identifiers, schema changes and both persistence editions. Existing users must be able to migrate to the new version without recreating saves or manually re-entering progress. A release is not ready until its migration path is implemented and verified.

- Support upgrades from every previously released data format, directly or through a tested migration chain. Do not assume users installed every intermediate release. Version persisted data explicitly when its structure changes.
- Migrate profiles, calculation snapshots/handbooks, checks, notes, delivery counts, custom tasks and active selections together. Preserve server ownership and browser-local isolation.
- For renamed, split, merged or removed steps, define explicit identifier mappings. Preserve original completion records when no unambiguous mapping exists and expose them for review; do not silently discard them or mark unrelated new work complete. Keep the original saved plan accessible when a replacement changes its meaning.
- Perform migrations atomically and make retries safe. Retain a recoverable copy of the pre-migration data before modifying it. Failed migrations must leave that data intact and present recovery guidance, never silently initialize an empty save. Automatic updates must not depend on the user having remembered to export a backup.
- Apply equivalent safeguards to IndexedDB and server files. Keep older full-save exports importable through the same version-aware migration path. Never downgrade or overwrite an unknown newer format; explain that a compatible app version is needed.
- Add anonymized fixtures for released formats and test direct/skipped-version upgrades, repeat attempts, partial-failure recovery and old exports. Verify exact progress and ownership preservation, not just that the new application opens. Migration tests are required whenever compatibility is affected.

- One deliberate exception, by the owner's decision (#51): removing an added storage bay also deletes the `slot-<address>` checks and notes of that bay's addresses, so a bay that later reuses the letter starts clean. The confirm dialog says so. The printed room's own bays (A–R, `STORAGE_ROOM` in `public/storage-room.ts`; `handbookBay` in `public/state.ts` keeps its old name) cannot be removed, only hidden (`storageBayHide`), which keeps all their records until they are restored; an added bay may take a printed bay's letter only while that printed bay is hidden and only with `replace`, after the user confirms: that clears the hidden bay's kept records first, the same exception (#167). One stored before these rules, sharing a letter with a printed bay still in the room, is removed without touching the printed bay's names or records. Records already orphaned by an earlier removal are left alone, because a reused letter makes their owner unknowable. Everywhere else the rule above holds.
- Ownership hierarchy: server user → named save → profile. Each profile owns its checks, notes, deliveries, selected phase and custom tasks. A user's stored active save and each save's active profile mean what the user opened last, which a new tab opens; each open tab keeps its own save and profile across reloads and writes only to it (#1052, view state in the tab's sessionStorage, never stored; see `public/AGENTS.md`), so the stored shape is the one every release has read.
- A new profile added to an existing save may start from a chosen sibling profile's records (`newProfileState` in `public/state.ts`, used by both editions). It copies, never moves: the source profile is untouched. World-shaped records (unlocks, the storage room, commissioning steps, deliveries, notes) copy as they are; plan-shaped `calc-` checks copy only where the new plan needs no more machines and no more input, and are carried unticked for review otherwise, matching `/api/round-up`. Creating a profile without `carryFrom` must keep producing the blank state earlier releases produced. The finished work a new profile may start with (`built`, `builtKeys` in `public/state/carry.ts`) is a production row of its plan, an `early-base-` step or an unlock: `unlock-`, `recipe-unlock-` and `hard-drives-<phase>` (#1068, the wizard's "What you already have"); anything else is dropped, and carried records still win.
- Calculated profiles retain calculation snapshots. Do not silently recalculate existing profiles during startup, navigation, import, or an application update.
- Edit settings recalculates a profile in place only when the user presses "Recalculate in place" (`POST /api/recalculate`, both editions, #1071): the profile keeps its id and gets the new plan, name and the progress `calculatedProfile` carries from itself (`recalculatedProfile` in `public/state/carry.ts`, the carry rules and picks of a new profile carried from it), with its revision moved past the previous one so a stale whole-value write from another tab is refused. The previous version is kept whole (plan, progress, payoff) as an ordinary profile named "<name> (before edit, <date>)" right after it, so nothing is deleted and no stored field is added: older releases, exports and imports read it as any profile. The request names the plan the edit started from (`planCreatedAt`); a profile recalculated since is refused (409), and a save without room for the backup (30 profiles) is refused; both write nothing. The plan's own recalculation offers ("Recalculate in place with exact clocks", "… with items made on site" and "… with transport fuel", `recalculateOffer` in `public/app/ui/recalc-offer.ts`) send the same request (`postRecalculation` in `public/app/recalculate.ts`): the plan's settings with the offer's change, the profile's own name and every carry pick (as the new profile they made before was carried), only after a confirmation that names the backup, and a 409 opens the plan the profile has now. "Round up production" still makes a new profile (`/api/round-up`, which copies all progress rather than carrying it).
- Items made on site (#868, #875): a factory group that marks an item (`factoryGroups.local`) gets its own whole-machine line for it in a recalculation the user starts, sized to that group's own consumers, and a central line covers the rest. The planner reads the groups only through the optional setting `settings.onSite` (`{ [groupId]: { name, items, shares: { [phase]: { [rowId]: share } } } }`), worked out by `onSiteSettings` in `public/app/on-site.ts` when the recalculation starts and frozen in `plan.settings` like `transportFuel`; the marks are set with the Factories page's "Made on site" picker (`factoryLocal` update, #877), and a changed mark only makes the page offer "Recalculate in place with items made on site" (the profile recalculated in place, progress carried, its previous version kept as a backup, #1071; see `public/AGENTS.md`), never a recalculation by itself; it is absent from every plan without it, which therefore calculates exactly as before (tested). A consumer row split over several groups is attributed by `rowShares`, measured against that row's total in the same phase of the plan being recalculated: fixed rates first, then the null-rate memberships split the rest; a row that plan lacks in that phase has a share only for its null-rate memberships, split evenly, and its fixed-rate parts count only where the recalculated plan builds it (`ifBuilt`, #1038, below). Shares and fixed-rate parts are per row id, as memberships are (#904): an amplified line (`amp:X`) and its unamplified twin (`X`) are separate rows everywhere, each with its own memberships, card and check key, and a recalculation carries memberships by the exact id (`mergeGroups` in `public/state/carry.ts`). So the planner reads a group's share (`shareOf`) and part (`phaseRate`) of a row by the row's own id only, with no fallback from one twin to the other either way, as `rowPlaces` places the row in the books: a group's line is never drawn on for a twin the books do not credit it with, and a twin only another group holds draws on that group's line alone. A group that holds only a recipe's amplified twin still gets its copy of the recipe making the item, because only the inner fit's pool holds the twins (`siteCopies`). In the solver (`planner/on-site.ts`) each such group gets a copy of each recipe whose main product is the item (its first output, `primaryOutput` in `planner/recipes.ts`; a recipe that makes it only as a byproduct, such as Rocket Fuel for Compacted Coal, stays central, because its copy would run the whole recipe and take over the group's own consumer, #1012), feeding a balance of its own (`item:<item>@<group>`, internal to the solve); the group's share of each consumer draws from it and the rest from the central balance, and a copy takes the items its own group marks (Copper Ingot for its Wire line) from that group's lines. Other inputs, byproducts, raw resources, existing supply and every demand stay central, except that the central byproduct of a marked item that balances exactly (a fluid such as Dark Matter Residue, which the Space Elevator part lines make) feeds the group's balance first (#1012, the owner's decision there; `siteFeeds` in `planner/on-site.ts`): a route `byproduct:<item>@<group>` from the central balance into the group's, a phase's routes of the item together capped by what the central lines make of it as a byproduct (`byproducts:<item>`), and preferred over the group's own line by a cost just below nothing (`BYPRODUCT_FIRST`, a tenth of a raw unit's), since both cost the same machines. So the group's line makes only the rest, and none when the byproduct covers the group's need: then no line is built, and the heading words the mark "(no line in this phase)" with no notice, because a recalculation plans it the same way. A solid byproduct has the sink and gets no route, so its group's line makes all the group uses, as before, and a phase without such a byproduct builds exactly the model it built before. The books need nothing new: the group's demand its own lines do not meet stays in `demand` and draws on the central supply, so the Logistics page shows the byproduct going into the group, and the plan's on-site warning adds a sentence per such item ("Central lines also make Dark Matter Residue as a byproduct, which cannot go to the sink: it goes to Gamma first, and Gamma's own line makes only the rest."). Copies are whole machines under `wholeMachines`, never amplified, not made for nuclear recipes, and a group with no consumer of the item in a phase gets no line there. A per-group line's row id is `<recipeId>:<groupId>` with `onSite: { group, recipe }` (`safeKey` allows `:`, not `@`, so its check key `calc-<phase>-<rowId>` is accepted by released versions), and its unlock and milestone are the recipe's (`recipeIdOf` in `public/progression.ts`). Such a line belongs wholly to its group while the group exists (`rowMemberships` in `public/app/group-order.ts`, which `rowPlaces`, `homeGroup` and `membershipsOf` in `app/views/factories.ts` go through; a saved assignment for its id counts only once the group is removed), so its card, its share and its build-plan step sit with that group; the step is titled "<item> for <group>" (`rowStepTitle`), and in the build order it feeds only rows with a share in its group (`sitesFeed`). On the Logistics page's books (`itemBooks`), its supply of an item the plan was calculated to make on site for its group (that group's `items` in the plan's `settings.onSite`, as the solver routes them: `siteItems` in `public/app/group-links.ts`, #1003) meets that group's own demand first and stays inside the group; what it makes beyond that goes to the sink (`sunk`), never to another group, so groups that make the same item on site have no link for it between them (#876). Any other output of the line is ordinary supply, as a central line's of the recipe: Water from its Aluminum Scrap line though the group marks Water (a raw resource the recalculation left out), or an item marked since. A mark cleared since changes nothing either, so the books, the flow page and the dialog describe the plan as it was calculated until a recalculation. The pages pass the plan's `settings.onSite`; without it (no plan has such lines without it) the group's marks stand in, as before. A group edit after the recalculation can leave the group asking for less than its line was sized to (#918): the sink still takes only the plan's surplus of the item, from each group in proportion to its excess, and the rest is `offered`, ordinary supply at the group that the other places share, so the books, the flow page and the factory dialog keep balancing without a recalculation (no notice asks for one); groups as the plan was calculated for offer nothing and come out exactly as before (tested against a recording), fixed-rate memberships included (#984, below), except for an item that balances exactly (a fluid) whose row with a fixed-rate membership changed its total in the recalculation. An own line's dialog note then says its group asks for less than it makes and where the rest goes, or that it asks for none and the sink takes all of it (#1002); it speaks of "the factory's other lines" only when the group has another own line for the item made on site for it, never for a byproduct, which a sentence of its own sends to the whole plan's demand (#1001). Any other line's note names the groups whose leftover meets part of the demand its rates leave out, and says "the other lines making it" rather than "the other recipes" when one of them copies its recipe (#1002). The factory dialog's flow (`calcFlowModel` in `public/app/flow.ts`) reads the same books for such an item (#956): a consumer's input links to the line that gives it most of the item (its group's own line), a group's own line delivers only to its group's share of each consumer and its excess to the sink, and the other lines making the item leave out what the own lines give; a phase without such a line reads no groups and draws exactly as before (tested). A recalculation that carries factory progress (`newProfileState`: in place, or into a new profile) cannot carry two kinds of tick onto one line: a ticked central line whose phase gains a group line of its recipe the source plan lacked, and a ticked group line the new plan no longer has (`siteTicksForReview`). Those are kept exactly in `onSiteReview.checks` (state version 15) and listed on the Notes page (`ui/notes/SiteReview.vue`, with ADA's `site-review` line); a central line among them that the new plan still has is unticked for review (counted in `reviewCount`), and the group lines start unticked. Nothing edits `onSiteReview`; a profile carried from one keeps it whatever the picks, and a share drops it with the rest of the progress. When the groups' lines make a whole-machine phase proven infeasible while it fits with the items made centrally, `solvePhase` plans it that way, last and for the whole phase, and records `onSiteDropped` (`{ groupId: items }`) with a warning and ADA's `on-site-dropped` line, as amplification and existing supply fall back; a search that only stopped keeps the lines through the stopped-search fallbacks.
- A central line of an item made on site that would sink almost all it makes (#1063): a group's own whole-machine line can make more than the group uses, and that excess has only the sink, so a central line could still be built for what the other consumers and storage ask and sink the rest (one Fused Quickwire machine for 1/min of storage, 89/min sunk). `withOverflow` in `planner/on-site.ts` (around `solvePhase` and, under minimal construction, `fullSpeed`, in `planPhase`) plans a whole-machine phase again when the central lines making such a solid item as their main product sink at least three quarters of what they make (`ALMOST_ALL_SUNK`; what they sink is the plan's surplus less the groups' excess as the model counts it, `sunkCentrally`): each such group's balance then gets a route into the central balance, `overflow:<item>@<group>` (the group's `overflow`, set only inside the planner, never stored), at a thousandth of a machine per item (`OVERFLOW_COST`), so it carries only what saves machines. The second plan stands only when it fits as the first did (no fallback the first did not need) and builds fewer machines in no more time, both plans compared as the goal leaves them: under minimal construction after `fullSpeed`, so a routed phase never finishes later at full speed than it would have without the route (tested with exact clocks). It records `onSiteOverflow` (`{ groupId: items }`) on the stage, which the plan's warning ("Phase 4: a central line would have sent almost all the Quickwire it made to the AWESOME Sink, so the own lines of Alpha also give the rest of the plan what they make beyond the factory's needs, and fewer central machines are built.") and ADA's calm `on-site-overflow` line (Factories and Logistics) state. Every re-solve of a finished stage (`fullSpeed`, the `phaseTime: 'final'` re-solves, the augmenter fuel verdict) reads its settings through `stageSettings`, which gives a routed stage its routes back (`withOverflowItems`), as it makes a stage with `onSiteDropped` central; `fullSpeed` keeps `onSiteOverflow` (and `onSiteDropped`) on the plan it returns, and so does `resolveEarlierPhases` on a phase it pulls ahead (`siteMarks`, #1099), so the warning and ADA still name that phase. Under `phaseTime: 'final'`, a routed phase that is not pulled ahead tries its first plan too (`withOverflow` hands it to `calculate()` as `unrouted`): when that one is pulled ahead to finish sooner than the routed plan, the phase keeps the first plan, pulled ahead, because the routed plan's capped re-solve may finish later than the first plan's (tested with exact clocks, Phase 3 at 5.56 h as before #1063, and the fallback itself in `tests/capped-refit.test.ts`). `resolveEarlierPhases` re-solves Phases 4 down to 1, so an earlier phase's caps hold the machines of the plan a later phase keeps. The books need nothing new: what the group's lines make beyond the group's use and the plan's surplus is `offered`, as after a group edit (#918), so the Logistics page, the flow page and the dialog show it going to the places that ask for it. Every other phase is planned exactly as before, and a stored plan keeps its lines and numbers until the user recalculates (tested in `tests/on-site-overflow.test.ts`, with the plan as stored before #1063). The property checks of #984 and #904 (`lineProblems` in `tests/helpers/on-site-books.ts`) allow such a group's lines to make more than the books give it, and its offer, only for the items in `onSiteOverflow`, and then only within the line's rounding beyond what the books give it and the offer, and with the groups' offers together at most the central demand.

Do not add new guards, fixes or tests for edge cases of this legacy input (#756, #761); close such issues as not planned with a link to #387.
- Keep IDs stable: save/profile IDs, recipe/factory IDs, checklist keys and storage addresses link existing progress to content. Display labels can change without changing these identifiers.
- Server writes are serialized and atomic. Preserve ownership checks, explicit save/profile scope, request-origin protections and optional authentication. A corrupt file must not silently become an empty workspace.
- Browser storage uses IndexedDB database `satisfactory-planner-browser-v1`, store `workspace`, record `main`. Preserve its name and transaction guarantees. Renaming the database makes existing saves disappear from the UI. A second key, `pre-handbook`, holds the record as it was before its original profiles were migrated (#497): written in the migration's own transaction, only while the key is empty, and never read by the planner. A third key, `pre-901`, likewise holds the record as it was before the first write that merged an amplified twin's unlock records (#901, below). The migration runs in the upgrade to IndexedDB schema version 2 (#518), so tabs of an earlier release get `versionchange`, close and say to reload, and a reloaded earlier release refuses the database as newer; a schema change needs such an upgrade whenever older tabs must not keep writing the old shape.
- Full transfers use `satisfactory-planner-saves`, version 1. They include plans/handbooks and progress, exclude credentials/accounts/sessions, and import as new copies with remapped IDs. An import leaves the user's active save as it was (`activeAfterImport` in `public/transfer.ts`, both editions, #1052; only a user without one gets the last imported save), and the Backup page names each copy after the file and its `exportedAt` before sending it (`labelImport`, "Coop world (from anna.json, exported 2026-10-04 14:05)", numbered " · 2" where that name is taken, within the 80 characters a name may have): only the names change, so nothing is stored that older releases cannot read, and a file without a usable date or name is labelled with what it has. Progress-only backups are a separate format. One restored onto a profile migrated from the handbook (`restoreProgress` in `public/handbook-migration.ts`, #606) is re-keyed as the migration re-keyed the profile when the backup has no `handbookOrigin` (it was made before the migration): by the profile's `handbookOrigin.mapping`, else, on the server, by the frozen handbook in `migrations/` when `handbookOrigin.version` matches it, else with every handbook-keyed tick, note and group assignment kept for review in `handbookOrigin.unmapped`. A backup with `handbookOrigin`, and any backup onto another profile, restores as it is. Profile shares (`/api/export-saves?save=…&profile=…&share=1`) are the same format scoped to one profile with progress stripped via `shareState`, so both editions import them through the normal path.

## Planning rules to preserve

Keep presentation separate from calculation. Do not change recipe rates, power budgets, goals or resource assumptions to make cards look cleaner.

- A profile is built for the phase it records in its settings. Do not offer or generate production for earlier phases (production lines, storage, power, hard drives, retirements): the user has already passed them, and each phase plan is a self-contained steady state that reads nothing from an earlier phase’s layout. A calculated profile still offers the phases before its start phase as milestone-only phases, listing only the milestones that belong there (the owner's answer on #570, #759: `milestoneOnlyPhase` in `public/progression.ts`, `firstPhase` and `milestoneOnly` in `public/app/session.ts`). The planner solves those stages too, but `calcStage()` reads none of them, so no page shows their production; a plan guide has no such phases.
- Where a phase stops using a line an earlier phase built, say so as a step: its budgets no longer include it, and a replacement is usually a different machine rather than an upgrade in place. Retire each line once, in the phase straight after the last one that needed it, and never one the plan picks up again later.
- Guidance must respect phase and milestone availability: early construction materials and biomass before later fuels, hard drives for alternates, relevant MAM unlocks, then later power and drone fuel upgrades. Each milestone a planned phase needs is one step, listed under its own phase (`milestonesListedIn` in `public/progression.ts`, #758): a HUB milestone under its tier's phase and a MAM node under the phase its costs first become available, a phase before the start phase included (#759). Every planned phase needs HUB Upgrade 6, Obstacle Clearing and Logistics Mk.2, because the biomass start-up steps and "Power available now" ask for them until a power unlock is ticked, so a profile made for a later phase lists them in Phase 1 (#781). Coal Power is needed from Phase 2 and Petroleum Power from Phase 3 whether or not the plan builds their generators (#1048), so a player who already runs them can tick them. "Power available now" never advises a power source below the one the player has ticked or the phase plans (#1048): with spare existing power in the settings (`availablePowerGW`), or Phase 5's Alien Power Augmenters, it says what the phase needs beyond that, from the stage's `requiredMW`, and the generation the plan builds for it (`generationMW` with the augmenters' boost, highest source first; the augmenters' own part is `availableMW` less that and the spare power, as `stageSupply` splits it, #1050 review) with what is left over and why (whole plants, Phase 5's waste-chain period, or the profile's minimum of uranium reactors), or that the spare power covers the phase; and the biomass start-up steps, and "Unlock Coal Power" unless the phase builds coal generators, are not listed then. A profile with Alien Power Augmenters needs the MAM node Power Augmenter, which Phase 5's augmenter step asks for: the augmenters are buildings, not rows, so the settings bring it in (#810). Its check key is `unlock-<id>` whichever phase lists it. Each alternate recipe a planned phase uses is likewise one unlock step, `recipe-unlock-<recipe>`, listed in the first planned phase (from the start phase on) whose lines use it (`hardDriveTasks`, #870), so ticking it never makes a later phase look started. A row's recipe is always `recipeIdOf` in `public/progression.ts`, never its row id: an amplified twin (`amp:<recipe>`) and a group's own line (`<recipe>:<group>`) share their recipe's unlock step, its title ("Unlock <recipe>", without "(somersloop amplified)") and its milestones, and so do the unlocks a new profile's picked alternates tick (`pickedRecipeUnlocks`) and the wizard's "Planner's choice" (`alternatesUsed`) (#901). Anything new that reads a recipe from a row goes through it.
- Within a phase the build plan lists the production steps group by group (`groupedSteps` and `groupedRows` in `public/app/group-order.ts`, #869), so a user finishes one site before travelling to the next. `phaseSteps` keeps the planner's order; `orderedPhaseSteps` in `app/views/calculated.ts` applies the profile's groups, and the build plan's steps and ids (`calcTasks`, `generatedTaskIds`) both come through it. Each row belongs to its home group (`homeGroup`: the existing group with the largest share of the row as `rowPlaces` places it, as the Logistics page and a group's flow count it, so a removed group's membership counts as Ungrouped and its fixed rate still takes its part (#900); on a tie, a membership with a fixed rate before an open one, then the earlier saved membership (#928); a part no group takes does not count. When no existing group has a share above `LINK_DUST`, the row is Ungrouped, where `rowPlaces` puts it: no memberships, only removed groups' memberships, fixed rates too small to count, or a total of zero (#942)), and rows in no group form one more place, Ungrouped. `groupedBuildOrder` keeps every step after the earlier steps (in the planner's build order) that make one of its inputs, and builds runs of one group: first a group that can be finished in one run, by the user's listed group order, else the group with the longest run possible now, so groups take one run each unless they need each other. Without groups, or with every row in one place, the order is the planner's exactly. Only the order changes: the startup, power, milestone, hard-drive, storage and retirement steps keep their places, every id stays, and a phase with a saved step order (`taskEdits.order`) keeps it, so personal tasks stay where the user put them. The build status breaks its ties in the same order. A step tied to one group (such as a per-group line, #876) is ordered by giving that group as its place.
- The build plan's focus (#1070, `phaseSteps` in `public/progression.ts`): a planned phase lists its startup and power steps, its required milestones, the power steps that ask for those unlocks (Phase 1 takes HUB Upgrade 6 straight after the HUB tutorial, since the biomass steps ask for it; later phases keep "Power available now" and the biomass start-up first, `powerStartupCount`), its mining and hard-drive steps, the production lines with each generator line straight after the last line making its fuel, or first (`powerFirst`, which `groupedSteps` applies again to the factories' order), storage, `deliver-<stage>` ("Send the Phase N delivery", not Post Phase 5), the storage-only lines, the retirements, and last the MAM research none of the phase's own lines needs (`optionalResearch`: listed there because its costs first become available, titled "… (optional)" with the phase that needs it). HUB milestones and the research `requiredMilestones` adds for every phase (Blue Power Slugs, Overclock Production) stay required. Phase 1 of a profile made for Phase 1 also has `space-elevator` ("Build the Space Elevator") before its lines. A step may be `optional` (research, storage-only lines), which the build plan's "Required steps only" hides (`requiredOnly` in `app/session.ts`, `planner-required-only` in localStorage, never saved), or `satisfied` while its own condition holds: `hard-drives-<stage>` with every recipe it lists ticked, and `deliver-<stage>` with every part's delivery count at its target (`deliveryKey`). A satisfied step reads as done everywhere steps are counted (`stepDone` in `app/tasks.ts`, the checklist, its progress bar, the phase track, the phase a profile opens on, ADA and `profilePhases` in both editions' summaries) with its reason under the title and its checkbox disabled; no tick is written. Every key stays as it was, so saved ticks mark the same steps (tested against the keys recorded before, `tests/fixtures/step-ids-before-1070.json`).
- A factory group's flow (`groupFlow` in `public/app/group-flow.ts`, #883, #893) is counted from the Logistics page's books (`itemBooks`, `groupLinks` and `sharedRate` in `public/app/group-links.ts`): each line is the group's share of a row (`rowPlaces` in `group-order.ts`; a part too small to count, a share at most `LINK_DUST`, is no line: `rowPlaces` gives it to the row's largest place, so a row's places add up to 1 and every row's links still add up to its rate, #906, while `rowShares`, which the planner reads, still leaves it out), in the build plan's order (`groupedRows`), and what comes in and leaves is `groupLinks`' own links, so the flow page and "Between factories" always agree. A group's own line made on site (#868) is therefore a card of its own in that group, feeding the group's own consumers first, and the page names each line as its build-plan step (`buildRowName`, so "Wire for Alpha", #896). Change how an item is shared out in `group-links.ts`, never in a copy. The flow page (`#factories/<group>/flow`, `ui/pages/GroupFlowPage.vue`, #894) is the group's one build-order view: "Build order →" on each group of the Factories page is a link to it, and it replaced the build-order dialog (#895), so there is no second ordering of a group's lines to keep in step.
- Every item, byproducts included, is shared out between places by one rule (#1022, #1028, the owner's choice C): `shareOut` in `public/app/group-links.ts`, which `groupLinks` applies to the books (`itemBooks`). Each place (a factory group, or Ungrouped) uses what its own lines make first; a place's leftover goes to the group short of the most, then the next, the largest leftover first, so each takes as few links as it can; what is still left goes to protected storage, drone fuel, vehicle fuel, the Space Elevator and last the sink; the raw resources and existing supply cover what is still missing. So no item goes both ways between two places, and no place both sends and receives one (a property test over real plans, `tests/byproduct-sharing.test.ts`). Inside a group (`insideLinks` in `group-flow.ts`) a line takes its own byproduct back first, then the group's lines share what is left in proportion to what each makes and still uses (`sharedRate`), and the ports reach the lines by what each still needs or has left (`portLinks`). The made-on-site books (`local`, `sunk`, `offered`, `siteItems`) keep their behaviour. A vehicle saved on a link (`factoryGroups.links`, keyed `<from>:<to>`) stays saved when the rule no longer draws that link, and applies again when it comes back. The byproduct advice (`public/app/recycle.ts`, no session imports) follows each place's links line by line (`placeLinks` in `group-flow.ts`): where each byproduct of a line goes (its own input first, "back to …, which feeds this line" for a loop, "in <group>" across groups; a solid's rest is "store or sink the other …", one no line uses "No line uses it: store it or send it to the AWESOME Sink."; a fluid never gets sink advice) and where an input a byproduct covers comes from. The factory dialog shows it under the flow (`ui/detail/RecycleAdvice.vue`), the build-plan step after its outputs (`rowStepBody` in `views/calculated.ts`, for the stage of the phase the step is in, never `calcStage()`; a step whose text the user rewrote keeps it), and a group's flow page as a ♻ line under the row (`ui/group-flow/FlowCard.vue`), with ADA's calm `recycle-byproducts` line on the factories page. Change the sharing in `group-links.ts`, never in the advice.
- Logistics advice must be buildable (#1067). How a link travels is one choice, `linkCarrier` in `public/app/logistics.ts`, which the Logistics page (`ui/factories/GroupLinks.vue`), a factory's flow page (its ports and their lines' links, through `linkItemWords` and `groupFlow`'s `carry`) and `transportFuel` all read: Water from the Water source is pumped by Water Extractors at the site that uses it (`EXTRACTED_ON_SITE`; no transport controls, and a vehicle saved on such a link stays saved but is not used), else the vehicle saved on the link, else belts and pipes. On belts, a link's solid items under a quarter of a belt (`TRICKLE_SHARE`), two or more of them, share mixed belts (`trickleItems`). A train's car loads through its platform's two ports (`PLATFORM_PORTS`), and the text names the cars. The factory dialog splits a line's machines over its destinations, the sink included, by largest remainder (`splitMachines` in `flow.ts`, `wholeShares` in `public/app/apportion.ts`), so the split adds up to the line's machines; `mach` keeps its old meaning. The byproduct advice gives a fluid that at least two lines of one place send and at least two ends take as one pool (`poolFor` in `recycle.ts`), rounded so its parts add up (`roundedParts`); everything else keeps the line-by-line advice. All of this is presentation: nothing stored changes.
- Whole-machine production is an option with recalculated upstream inputs and surplus. Do not merely round displayed machine counts and claim the material balance still holds.
- Whole machines at 100% stay the default (owner, #1066), and the plan shows what they cost: each phase of a whole-machine plan records `exactPlan` (`withExactPlan` in `planner/calculate.ts`: the same phase planned without `wholeMachines`, its buildings, `needMW` (the power it needs as the pages give it: its grid's, #1064), raw resources, summed surplus and hours; absent from exact plans, from a phase whose exact plan does not fit and from plans calculated before it), which the build plan's side column (`ui/plan/RoundingCost.vue`), the wizard's Review, its Goals step and live estimate (`measuredRounding` in `public/app/exact-clocks.ts`) and ADA's `rounding-cost` line set beside the whole-machine figures. A stored plan without it shows nothing until the user recalculates. Any production line that rounds (`roundsToWholeMachines`; the interface's copy is `roundsWholeLine`, checked against it on every recipe) can run at exact clocks instead: `settings.exactClocks` (`{ phase: [row id] }`, validated by `settings()`, never an `amp:` twin, absent unless a recalculation the user started asked for it) keeps that phase's line fractional in the whole-machine fit (`exactClockLine` and `wholeLine` in `planner/model.ts`, which the rounding fallbacks follow through `model.ints`, and the rounding warnings leave out). The user picks it in the line's dialog (`ui/detail/ExactClockChoice.vue`), stored in the progress state (version 16, above); the build-plan step and card say what a recalculation would change (`lineClockNote`), and `ui/plan/ExactClocksRecalc.vue` on the build plan and Factories page offers "Recalculate in place with exact clocks", the profile recalculated in place with progress carried and its previous version kept as a backup (#1071) (ADA's `exact-clocks-pending`). A plan without the field calculates exactly as before (tested). Fluid, generator and nuclear lines always run at exact clocks, and the dialog says so instead of offering the box. A fluid line is one whose main product (its first output, `primaryOutput`) is a fluid, also when it makes a solid beside it (#1086: Rocket Fuel with its Compacted Coal, Fuel with its Polymer Resin, Alumina Solution with its Silica), so its fluid is never rounded up and its solid follows it into the sink. Every plan since records `exactFluidLines: true`; a plan stored before rounded those lines to whole machines and keeps them, and its dialog keeps offering the box for them (`fluidLines` in `public/app/exact-clocks.ts`), until the user recalculates.
- Minimal construction is the fewest buildings that deliver each phase within its 24 hours, run as fast as they allow (#1066, `fullSpeed` in `planner/adjustments.ts`): after the 24-hour solve the phase is solved for maximum output with every row, generators included, capped at the machines the 24-hour plan builds (`caps`, as `phaseTime: 'final'` caps an earlier phase), and that plan is kept when it finishes strictly sooner, with `aheadOf` the 24-hour plan's hours (Review's "was …") and a warning naming the phases. Phase 1 runs on hand-fed biomass, whose maximising solve has only the spare power, so it keeps its 24-hour plan. Measured on a default plan, the busiest line (Copper Ingot in Phase 5) leaves only a little speed to gain: the low clocks are lines a phase needs only a trickle from, each a single machine either way.
- A whole-machine draft (`wholeMachinesReason` in `planner/draft.ts`) measures the least extra budget whole machines need: the integer fit over the exact plan's network may draw beyond each budget only at `OVER_BUDGET_COST` per item per minute (`overBudget` in `run`'s options), up to the budget plus 600/min. It used to double every budget, where raw resources cost almost nothing, so the fit spent the room on saving machines and named resources it did not need (#1066: Copper Ore on an impure 5× Phase 5 that needs only more Crude Oil). That fit keeps the exact plan's network, while the plan with the raised budgets picks its own, so the named amounts are checked (`checkedShortfalls`, #1091): the phase is planned as calculate() plans it (`replan`) with each budget raised as the draft's fix words it, and while that is proven short, measured again from there and raised, at most three plans, which only a whole-machine draft pays for. An amount still short, or whose check stopped at a search limit, is marked `atLeast` and the fix says "to at least" instead of "to about".
- All of a Space Elevator part's output goes to the elevator (#1062): `deliverAll` in `planner/stage.ts` sets each part's delivery `rate` to everything its central balance has left beyond the lines, storage, fuel and the other demands (the model still plans for the goal's rate, the balance's lower bound), so no part goes to `surplus` and `hours` follows what the lines really make (Phase 3's two Versatile Framework Assemblers deliver 10/min, 4 h 10 min, not the goal's 5.3/min). An excess of at most 0.002/min changes nothing, so a plan without whole machines reads exactly as before. A stored plan keeps its rates, surplus and hours until the user recalculates; it needs no migration, because the shape is unchanged. A part counts as delivered once its saved count reaches the target (`public/app/delivered.ts`, read beside the plan, nothing stored): the build plan dims the steps of the lines that make only delivered parts (none of their products feeds another line of the phase, an unfinished delivery, storage or fuel), puts them after the other unfinished steps and never leads with one, with a note naming the first later phase that builds the same row id ("now only needed for Phase 2") or none; nothing is ticked, and Post Phase 5 dims nothing. The summary gives the time the rest of the delivery takes, Logistics marks the part delivered on its link to the elevator, and ADA's `delivered-lines` line counts the dimmed steps.
- When a phase's whole-machine search stops at a solver limit (node limit, backstop or the phase's deadline) without a plan while the exact plan fits, `roundedFallback` in `planner/rounding.ts` rounds the exact plan's network to whole machines instead (the owner's decision in #593), with linear solves only (`roundedRun`). The deliveries are drawn at one `pace` (at most the phase's rates), and every fractional whole-machine line is rounded to its nearest whole count (at least one machine) and the model solved again, until all are whole, so the lines feeding them follow the material balance. A line nearest a higher count gets it as a minimum; one nearest a lower count gets it as a cap, which lowers the pace, so the phase takes longer. Each solve first exceeds the caps as little as it can, so a cap holds unless the lines it feeds need more; a line over its cap is rounded up from then on. Amplified twins are rounded down. It tries the target time, then 5%, 10%, 25% and 50% longer (`ROUNDED_STRETCH`), amplified before unamplified at each time; at each time first to the nearest count, where lines rounded down may slow the phase only to the next time (at the last, not at all), then with every line rounded up, which needs more resources but no more time. A line rounded up more than `ROUNDING_RAISES` times is left fractional and named in the warning (`raisedLines`): two whole lines tied by an exactly balanced fluid take turns without end, and only a line that makes or uses a non-raw fluid another whole line of the stage also makes or uses is said to share a fluid; a line at the top of a long chain (Iron Plate, Copper Ingot) reaches the limit too, and the warning says it kept being rounded up as the lines it feeds were rounded (#714). The stage records the exact plan's time as `roundedAfterStop` (#708: under the balanced goal the rounded rates make the exact plan itself take 8.33 hours, so comparing with the goal's 8 would blame the rounding for time it did not add); the warning and ADA (`rounded-after-stop`) say the search stopped before it could prove the best plan, that the exact plan was rounded to whole machines (not "to the nearest": the rounded-up plan may be the one used, #698), and how long the phase takes against the exact plan. Only `solvePhase` asks for it (`roundStopped`), never the draft diagnostics, the `phaseTime: 'final'` re-solves or the unfueled comparison, so a search that finishes plans exactly as before. When no rounded plan fits even 50% longer, `easyClockFallback` plans the exact plan's network with fractions that are easy to set (#694): the same rounding at the same times as `roundedFallback` (`ROUNDED_STRETCH`, shortest first, nearest then all up; by the owner's decision in #701, since under maximum output the quarter grid can fit only from 10% longer, an easy-clock plan up to 50% longer is preferred over precise clocks at the target), at each time easy clocks before rate clocks and amplified before unamplified, on a finer grid (`lineGrid`): every solid-part line runs whole machines at 100% except the last, first at 25%, 50% or 75% (`'easy'`), then also at any clock where it makes a whole number of its product per minute (`'rate'`). Amplified twins and uranium plants stay whole. The finer grids give each raise less to spare, so they allow more raises and passes (`EASY_RAISES`, `EASY_PASSES`). When neither fits, or the shared `ROUNDING_MS` runs out, the phase is the exact plan itself with its precise clocks (`'precise'`), which always fits, so a stopped search never costs a phase. The stage records `fractionalAfterStop` (the exact plan's time as `target`, and the clocks); the warning and ADA (`fractional-after-stop`) say plainly that the phase is not whole machines because the search stopped before it could prove the best plan.
- Under whole machines the uranium plant count is whole (#370). In Phase 5 under `recycle` it is a multiple of the waste chain's period (`nuclearPeriod`, 20 with the default recipes), so every waste line, the plutonium and ficsonium plants included, runs whole at 100%; the extra plants only add generation. The fuel feed stays fractional, because radioactive items balance exactly. When whole plants do not fit the budgets, the fit falls back to the fractional count and sets `nuclearFractional`, as amplification and existing supply fall back.
- `phaseTime: 'final'` applies the target time to Phase 5 and re-solves phases 1–4 for maximum output under per-recipe caps (`caps` in `run`): each recipe is limited to the machines some phase from that one onward already builds, and a recipe no such phase uses is capped at zero. A phase is replaced only when it finishes strictly sooner, and it records `aheadOf` so the interface can show what it used to take. The default `'every'` must keep producing the per-phase plan earlier releases produced. Do not let this add capacity a later phase drops — that is the whole point of the caps, and it is tested. A capped re-solve (this one and minimal construction's `fullSpeed`) fits in two steps like any other (`twoStepFit` in `planner/fit.ts`), so a looser cap could make the exact LP pick a network the integer fit cannot round, and the phase read as unable to finish sooner (#1094). When the integer fit over the exact LP's network is proven infeasible under caps, `cappedRetry` fits once more over that network widened with every recipe the caps allow, which holds the stage's own rows, so a plan that fits under tighter caps never turns infeasible under looser ones; a fit that works the first time, or whose search stopped, is used as before (tested in `tests/capped-refit.test.ts`).
- Storage selections protect the selected outputs. Unpackaged fluids and radioactive items do not belong in the general storage contract. Gathered items may have storage positions without being continuously produced.
- The protected rate is per item, not global: `storageRateFor` in `public/preferences/storage.ts` resolves a per-item override, then Space Elevator parts at 0 (`elevatorParts`, in the same file, kept in step with the planner's `DELIVERIES` by a test — their deliveries and the later project parts consuming them are already planned, so a buffer on top is production nobody draws from), then the construction-material rate (`buildRate`), then the general rate (`storageRate`). An absent `buildRate` must keep meaning "the general rate", so profiles saved before it existed calculate identically. A rate of 0 keeps the item's container and storage address while reserving no production — keep such items in `stage.storage` so the storage map still shows them, and out of rate listings.
- Protected storage takes surplus first (#1061, the owner's rule): under whole machines with `settings.storageFromSurplus` (set by the wizard's drafts, `newDraft` in `public/app/wizard/wizard.ts`, and by Round up production, `roundUpSettings` in `public/state/carry.ts`; absent from every plan stored before, which keeps its lines and numbers until the user recalculates, and from plans calculated without it, which plan storage as a demand exactly as before, tested), storage is not a demand of the phase's solve (`stockedFromSurplus` in `planner/model.ts`). `withStock` in `planner/stock.ts` adds it after every adjustment and before `carryGenerators`: an item the plan makes a surplus of takes its rate from that surplus, at most the rate, with no extra machine; only an item with no surplus gets storage-only lines (`<recipe>:stock` rows with `stock: { recipe }`; `recipeIdOf` reads it), and an item with a per-item rate of its own (`storageOverrides`) is topped up to it the same way. Those lines come from one linear program at exact clocks over the phase's recipes, fed by the plan's remaining surplus, the raw budgets and existing supply it leaves, and power paid for with fuel (the generators' burnt fuel beyond the need, then more fuel in their whole generators, then generator lines of their own, solved again with the underclocking credit, so the fuel covers the need as `withinLoad` keeps it, #1086); fluids balance exactly, so no fluid is made for storage beyond what its Packager takes. The stage's `storage` is what storage receives (so the books balance) and `storageAsked` what the settings ask. The build plan lists the storage-only lines after the storage step, titled "… for storage (optional)" (`groupedSteps` leaves them there), the storage step and the storage room's step say surplus first and overflow to the AWESOME Sink, the Resources page says each container's source (`storageSources` in `public/app/storage-source.ts`), Review counts their buildings, a line's dialog says it runs at exact clocks, and ADA has `storage-lines`. Tested in `tests/storage-surplus.test.ts`.
- Production you already run (`existingSupply`) is a per-item rate the plan credits: a capped, almost-free source of that item, modelled exactly like a raw-resource source. The plan then builds only the remainder and never the chain behind it. It is deliberately a rate rather than a match against the plan's own rows, because an existing factory rarely uses the recipe or machine count a fresh solve picks. Its ore and power are assumed to be outside the entered budgets, the same assumption "spare existing power" already makes. An empty map must keep producing the plan earlier releases produced, and it is tested. Crediting a line narrows the recipe network the exact solve chooses, which leaves less room to round up to whole machines: widen the network with the recipes the phase would have used without the credit, and if it still will not round, drop the credit and set `supplyDropped`. Telling the planner what you already built must never cost you a plan — the same rule production amplification follows.
- Existing supply and items made on site may name only a known item that is not a raw resource (`suppliable` in `planner/settings.ts`), and the planner refuses a request naming any other. ## ADA

`public/ada.ts` holds ADA’s remarks: facts in, ordered plain-text lines out. `adaFacts` in `public/app/ada-panel.ts` builds those facts from the same counters the pages render, and escapes the text like any other untrusted name.

**When you add a feature, add ADA’s lines for it in the same change.** A new counter, warning, page or editing mode that ADA cannot see is a gap users notice. Give the rule a stable `id`, an `on` page affinity, a `tone` (`calm`, `warn` or `praise`), `lead: true` only for a state that makes everything else irrelevant (it ranks first), and cover it in `tests/ada.test.ts`.

Keep the deal the feature rests on: the joke is in the tone, never in the numbers. A remark may only restate what the plan already contains — including repeating the planner’s own infeasibility reason rather than inventing one — must never imply the app has altered saved progress, and must not be the only place some piece of guidance appears. Rules are skipped rather than thrown from, and the panel is wrapped in a guard: ADA must not be able to break the shell.

Run commands from this repository root. Node 24 is used in CI; the package supports Node >=22.18 (the first 22.x that strips TypeScript types without a flag). The frontend was migrated to Vue 3 in stages, now all done; see "Vue migration" in `public/AGENTS.md`. Source files stay readable: `npm start` serves `public/` unbuilt, compiling the `.vue` files through Vite in middleware mode (see `devFrontend` in `server.ts`) unless `NODE_ENV=production`, and only `build.ts` minifies, for publishing.

```sh
npm ci
node server.ts
npm run check
npm run typecheck
npm test
npm run build
```

`npm run check` is Prettier; run `npm run format` rather than hand-compacting code. `npm run typecheck` is `vue-tsc --noEmit` (see "TypeScript" below). `npm test` runs `node --test` on `tests/*.test.ts` and then Vitest on the component tests in `tests/ui/`; it needs `npm ci`. The VM-based interface tests load the `public/app/` modules through `tests/helpers/app-source.ts`, which concatenates them in ES evaluation order: top-level names must stay unique across those modules, and a module changes another module's `let` only through that module's exported setter. The harness leaves out the Vue layer (`vue` and `public/app/ui/`), follows its imports of plain modules, and replaces the names plain modules import from it with do-nothing functions. It strips the types from a `.ts` module first (`stripTypeScriptTypes` from `node:module`), which leaves the rest of the text as written.

The component tests in `tests/ui/` import `node:assert/strict` as usual, but `vite.config.ts` points that import at `tests/ui/assert.ts` (#287). Plain `node:assert` prints both sides of a failed check at depth 1000, and a happy-dom element reaches the whole document and window, so a failed `assert.equal(document.activeElement, $('#x'))` or `assert.equal($('#x'), null)` hung for minutes and then crashed the Vitest worker. The wrapper's `equal`/`strictEqual`/`notEqual`/`notStrictEqual` report a DOM node by a short name such as `<button#save.primary[data-confirm-ok]>`; everything else is node:assert's. Compare page elements only with those identity checks: not with `deepEqual`, which still prints the whole node (compare an `id`, text or attribute instead).

### Structure

Keep each function about one thing and each module about one concern, so a change touches one small piece and a reviewer can follow it (#504). Long functions and catch-all modules are being split in sub-tasks of #504; new and changed code follows these rules now:

- A function that grows past about 60 lines, or nests blocks more than three deep, is split before more is added to it: pull each step out into a named function that says what it does, and keep the original as the short list of those steps. Prefer extracting over growing a function.
- A dispatcher over many cases (an HTTP route, an update `type`, a wizard step) is a lookup from the case to one named handler, not an `if`/`else` chain holding every handler's body. `mutate` in `public/state/mutate.ts` is the pattern: `stateEditFor` looks an update up in `recordEdits` or hands it to its family, and `mutateLayout` there looks a storage update up in `layoutEdits`, a table of one function per storage update type.
- One concern per module. A module that validates saved data should not also hold page text or seed data; when a module mixes them, move one out rather than adding a third. A new root script in `public/` is listed in `build.ts` (see "TypeScript").
- The two editions share logic instead of copying it. A rule both the server (`workspace.ts` and its handlers in `server/`) and the browser edition (`public/browser-api.ts`) apply, such as which checks a new profile carries, lives once in a shared module (`public/state.ts`, `public/transfer.ts`) and both call it; only transport, storage and error reporting stay per edition. Fixing a copy in one edition and not the other is how the editions drift apart.
- Repeated blocks become one helper with a name, when they mean the same thing (not merely look alike). Delete dead code rather than commenting it out; git keeps the history.
- A structural refactor is a pure refactor: no change to behaviour, error messages, saved data, request and response shapes or the interface. Existing tests pass unchanged, and an extracted unit that was hard to reach before gets its own focused test.

### TypeScript

All code is TypeScript. It moved one module at a time, in stages like the Vue migration: (1) the tooling, with `public/app/format.ts`, `ui/ItemIcon.vue` and `ui/StatTile.vue` as the first typed files (done); (2) types for the saved progress state (`state.ts`, every version), the legacy handbook, the calculated plan and the workspace, in `public/types/` (done); (3) the plain modules in `public/`, in two pull requests: (a) everything under `public/app/`, which Vite bundles (done), then (b) the shared scripts at the root of `public/`, which the server imports too and `build.ts` ships as separate files (done); (4) the components (done); (5) the server, `workspace.ts`, `planner.ts`, `optimizer.ts` and `docker-start.ts`; (6) the build tooling (`build.ts`, `browser-check.ts`, `vite.config.ts`) and the tests. Each stage was its own pull request and left both editions working. No JavaScript is left in the repository: the solver (`highs`) and the typefaces (`@fontsource/*`) come from npm, pinned in `package.json`, and `highs` ships its own types. `highs` is the one runtime dependency, which the Docker image installs with `npm ci --omit=dev`; everything else is a dev dependency.

Nothing compiles TypeScript to files: Vite and Vitest strip the types when they serve, test or bundle the code, esbuild when `build.ts` minifies, and Node 24 itself when it runs a `.ts` file. `tsconfig.json` only drives the type check (`npm run typecheck`, also in CI), with `strict`, `noUncheckedIndexedAccess` and `noUnusedLocals` on (an import or local nothing reads fails the check; delete it rather than silencing it). Rules:

- Use only syntax Node can erase (`erasableSyntaxOnly`): no `enum`, `namespace` or constructor parameter properties. Use a union of string literals or an `as const` object instead of an enum.
- Import a TypeScript module by its `.ts` file name (`'./format.ts'`), as Node requires; import types with `import type` (`verbatimModuleSyntax`).
- No `any`, no double cast (`as unknown as X`) and no `@ts-ignore`. The one double cast is in `tests/types/fixtures.ts`, for a JSON import, and says why; `tests/double-casts.test.ts` fails on any other, in any form (bracketed, broken over lines or with angle brackets). The node tests read the frozen handbook (`migrations/handbook-2026-09-13.json`) and `recipes.json` typed from `tests/helpers/data.ts`, the component tests from `tests/ui/setup.ts`, rather than casting a JSON import. A value from outside (saved data, a request body, an import, JSON) is `unknown` until a check narrows it; keep the run-time checks for those even where the types look sure. A single `as` is for a value a comment can vouch for (a form field whose options are the allowed values, a partial test fixture). `@ts-expect-error` only where code deliberately passes a wrong type, as a test of rejected input does.
- Types describe the code; they never change saved data. The data types live in `public/types/` (types only, left out of both builds; import them from `public/types/index.ts`). Saved data has two shapes there: `ProgressState` is what `validateState` returns and `SavedState` any released version it accepts; `CurrentCalculatedPlan` is what `calculate()` returns today and `StoredCalculatedPlan` any plan an earlier release froze on a profile, so a field added to the planner is required only in the Current types. Read saved data through the Stored types.
- `tests/types/data.types.ts` checks the types against the frozen migration handbook (`migrations/handbook-2026-09-13.json` against `Handbook`, the converter's input type) and a plan frozen by the first release's planner (`tests/fixtures/calculated-plan-2026-09-12.json`), both ways: the data must fit the types and hold no field they do not declare. `tests/types/fixtures.ts` has a typed state for every version, which `tests/data-types.test.ts` runs through `validateState` and `validateTransfer`. When the saved shape changes, add a fixture of the new shape and keep the old ones.
- The entry points that read or produce saved data (`validateState`, `mutate`, `initialState`, `newProfileState`, `shareState`, `calculate`, `settings`, `catalog`, `validateTransfer`) declare these types in their signatures. A type that does not resolve silently becomes `any`; `data.types.ts` pins each one, so keep it in step when changing a signature.
- Look up a page element the frame or the current screen always has with `required(selector)` (`app/format.ts`), which throws naming the selector; keep `$(selector)` and a null check for one that may be absent. Code that only runs while the wizard is open reads the draft through `draft()` (`app/session.ts`), which throws when there is none; code that may run without one reads `wizard` and checks it.
- A non-null assertion (`!`) needs a comment saying why the value is there (a filter just above, a loop bound), unless it is plain from the line itself.
- Every component is `<script setup lang="ts">` with type-based `defineProps<{ … }>()` (`withDefaults` for defaults), so vue-tsc also checks its template against those types. A prop takes a named type (`PlanStepView`, `FlowModel`, `StorageBayView`, …), never `Object` or `Array`; `GroupSections.vue` is generic (`generic="T"`) over the items it groups. Event handlers type their event (`e: Event`) and cast its target to the element they are bound on. An attribute a template drops is bound to `undefined` (DOM typings refuse `null`; Vue removes the attribute for both).
- Every script at the root of `public/` is TypeScript and ships as `.js`: `build.ts` strips and minifies each shared one (`SHARED`) with esbuild and rewrites its `./x.ts` and `../x.ts` imports to `.js`, and bundles `app.ts` (which `index.html` loads in development) into `app.js` (`BUNDLED`, with `app-root.ts`). A new root script must be added to `SHARED` or `BUNDLED` there; so must a new module in a shared folder (`SHARED_DIRS`: `public/state/` and `public/preferences/`), which ships under the same folder.
- The server imports the shared sources (`./public/state.ts`, `transfer.ts`, `handbook-migration.ts`, and `preferences.ts` through the modules of `planner/`) and Node runs them as they are. The Docker image therefore copies `public/*.ts`, `public/state/*.ts` and `public/preferences/*.ts` next to the built `public/` (a new shared folder needs its own `COPY` line), and `server.ts` answers 404 for any `.ts` path so browsers only ever get the built files. The Docker smoke test in CI starts that image, so a server import the image lacks fails there.
- The server-side modules (`server.ts`, `workspace.ts`, `server/`, `planner.ts`, `planner/`, `optimizer.ts`, `docker-start.ts`) run as they are in the Docker image, which copies each by name (the `Dockerfile` `COPY` lines): a new server file or folder is added there, or the image fails the smoke test. A request body is `unknown` until a check narrows it; keep the existing checks rather than trusting a cast. The Pages edition ships `planner.ts` as `planner.mjs`, each module of `planner/` as `planner/<name>.mjs` and `optimizer.ts` as `optimizer.mjs`: `build.ts` strips them (`plannerJs`), replaces a few snippets by exact match (in `planner/data.ts` only: the `node:fs` import, the `recipes.json` read; in `optimizer.ts` the `highs` import), and renames the planner's import paths with `plannerImport`, so keep those snippets unchanged.

### Naming

Name variables, parameters and helpers for what they hold, in words a reader understands without looking up where they came from (#503): `user`, `profile`, `draft`, `entry`, `checkKey`, not `u`, `p`, `d`, `v`, `k`. Rules:

- A single letter only for a counted loop index (`for (let i = 0; i < rows.length; i++)`) and for the parameter of a one-line callback whose collection says what it is (`saves.filter(s => s.userId === user.id)`, `profiles.find(p => p.id === profileId)`). A callback that spans several lines, or whose parameter is not an item of the collection it is called on, gets a full name: `commit(draft => { … })`, `users.find(account => account.id === userId)`.
- No private abbreviations: `error`, not `e`, in a `catch` or error callback; `phase`, not `ph`; `input`, not `b`, for a request body. Names every Node or DOM example uses (`req`, `res`, `url`, `id`, `el` for an element) may stay.
- A rename is a pure refactor: it never renames what leaves the code (JSON keys, saved state fields, request fields, `data-*` hooks, form field names, exported names other modules or tests import). Keep comments in step with the new name.
- Existing code is being renamed area by area in sub-tasks of #503; new and changed code follows these rules now.

The server defaults to port 8080. Set `HOST=127.0.0.1` for a local-only preview and `DATA_DIR` to an isolated temporary folder for experiments. Environment-variable syntax differs by shell. Check whether an existing server is running before starting another; never terminate unrelated processes.

For real-browser verification, Playwright is a pinned dev dependency (`npm ci` installs it, without a browser); CI then downloads Chromium:

```sh
npx playwright install --with-deps chromium
npm run build
node browser-check.ts
```

`PLANNER_PLAYWRIGHT` can point to an already installed Playwright entry file. `PLANNER_BROWSER_CHANNEL=msedge` can use installed Edge. Browser checks serve the build under `/satisfactory-planner/`, run the actual WASM calculator, and test persistence, isolated profiles, concurrent tabs and Docker transfers in temporary storage.

Use tests appropriate to the change. UI redesigns require real-browser inspection in addition to tests; see `public/AGENTS.md`. The VM-based interface tests currently reference UI functions/selectors. If restructuring them, update the tests to cover equivalent behavior rather than deleting coverage. Documentation-only changes need link/path and diff review, not the whole Docker test suite.

## Backlog and issues

The backlog (bugs, feature requests, cleanup) lives in GitHub Issues on `reinder83/satisfactory-planner`, and nowhere else: no TODO files, notes in these guides, agent memory or task lists that could drift from it. The owner adds requests there too. Read it with `gh issue list -R reinder83/satisfactory-planner`.

- Every possible bug you find goes in as an issue straight away: one noticed in passing, one a helper or subagent reports, and one traced from the code but not reproduced. Don't fix it on the side or only mention it in your reply; link the new issue in your reply and carry on with the current task. A defect inside the change you are making may be fixed in that change; say so in the pull request, and still file an issue if it was already on `main` and the fix is out of scope.
- A message that says "for the backlog", or a bare bug report with no request to fix it, means file an issue and stop. Offer to fix it; don't start.
- Give each issue a type label (`bug`, `enhancement` or `cleanup`) and a priority (`priority: high`, `priority: medium` or `priority: low`). Add `unverified` when it was traced from the code rather than reproduced, `saved data` when it touches saves or progress (follow "Data compatibility is essential"), `needs decision` when the owner must choose the behaviour first, and `fix ready` when a branch with a fix exists. Name the file and the concrete failure.
- When asked what to work on, list the open issues by priority. A fix pull request says `Fixes #N`.
